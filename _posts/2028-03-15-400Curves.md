## Overview

400Curves is a Medium crypto challenge. You connect over TCP, hand the server a
point `(x, y)`, and it returns `d * (x, y)` where the secret scalar `d` **is the
flag** (`d = bytes_to_long(FLAG)`). The server uses the NIST P-256 curve
parameters but never validates that your point is actually on P-256 — and its
group law only ever touches `a` and `p`, never the curve constant `b`. That is a
textbook [invalid-curve attack](https://cwe.mitre.org/data/definitions/20.html):
feed points from weaker curves, recover `d` modulo many small primes, and CRT
them together.

## The technique

The server code:

```python
a = 0x...fffffffc          # NIST P-256 a
b = 0x5ac635d8...604b      # NIST P-256 b
p = 0x...ffffffff          # NIST P-256 prime
E = {'a': a, 'b': b, 'p': p}

def multiply(P, n, E):     # double-and-add — uses only E['a'], E['p']; NEVER E['b']
    ...

# per request:
x, y = map(int, recv().split())
S = multiply((x, y), bytes_to_long(FLAG), E)   # d = long(FLAG)
send(f"Shared secret: {S}")
```

Elliptic-curve point addition in short Weierstrass form is identical for every
curve `y² = x³ + ax + b'` that shares the same `a` and `p` — only `b'` changes,
and `b'` is just `y² − x³ − ax mod p`, silently determined by whatever point you
send. So:

1. Pick a curve `E_{b'}` whose group order `|E_{b'}|` has a small prime factor `r`.
2. Build a point `P` of order exactly `r` on it.
3. Send `P`. The server returns `S = d·P`, which lives in the tiny order-`r`
   subgroup, so `S = (d mod r)·P`.
4. Discrete-log over `[0, r)` (BSGS) → `d mod r`.
5. Repeat for enough small primes that their product exceeds `d`, then CRT.

**Counting points without SageMath:** `pip install cypari2` ships a manylinux
wheel that bundles PARI, and `pari.ellcard(E)` runs SEA on the 256-bit field in
milliseconds. Trial-divide the order by a small-prime sieve — no full
factorization needed, the huge cofactor is irrelevant.

### The broken group law (the real crux)

Half of the queries came back as off-curve garbage and BSGS failed. The reason
is a second bug in the server's `add`:

```python
if ((x1 == x2) & (y1 == -y2)):   # inverse-point check
    return ((0, 0))
```

`-y2` is the **unreduced** negative integer, but `y1, y2 ∈ [0, p)`, so
`y1 == -y2` is essentially never true. The server therefore never returns the
identity for `P + (−P)`. When the double-and-add chain for the big scalar `d`
internally adds a point to its inverse, `x2 − x1 == 0`, so it computes
`inverse(0, p)` — and pycryptodome's `inverse(0, p)` returns `0` (it does **not**
raise). The slope becomes `0` and the "sum" is `(−2·x1 mod p, −y1 mod p)`: a
bogus point that is neither on the curve nor the identity.

So for each point `P` of order `r`, the oracle's answer is **either** the correct
`d·P` (BSGS recovers `d mod r` — a *good* prime) **or** off-curve garbage (BSGS
fails — a *bad* prime). Which one is deterministic in `(P, d)`, and roughly half
the primes are good. Since the flag `d` is baked into the challenge, `d mod r` is
the same across every instance — so you accumulate good residues across
reconnects, skip the bad primes, and CRT once the good product exceeds `d`.

## Solution

The durable solver. Point-hunting uses PARI; all EC arithmetic is hand-rolled to
match the server (identity `(0,0)`), and the online phase persists good residues
so it survives the short-lived docker instance dying mid-run.

```python
import socket, os, json
from math import isqrt
from functools import reduce
from Crypto.Util.number import long_to_bytes
from sympy.ntheory.residue_ntheory import sqrt_mod
import cypari2

pari = cypari2.Pari(); pari.allocatemem(1 << 30, silent=True)
a = 0xffffffff00000001000000000000000000000000fffffffffffffffffffffffc
p = 0xffffffff00000001000000000000000000000000ffffffffffffffffffffffff

def inv(x): return pow(x % p, -1, p)
def add(P, Q):
    if P == (0, 0): return Q
    if Q == (0, 0): return P
    x1, y1 = P; x2, y2 = Q
    if x1 == x2 and (y1 + y2) % p == 0: return (0, 0)          # correct identity check
    l = (3*x1*x1 + a)*inv(2*y1) % p if P == Q else (y2-y1)*inv(x2-x1) % p
    x3 = (l*l - x1 - x2) % p
    return (x3, (l*(x1 - x3) - y1) % p)
def mul(P, n):
    R = (0, 0)
    while n > 0:
        if n & 1: R = add(R, P)
        P = add(P, P); n >>= 1
    return R

def bsgs(P, S, r):                                             # dlog in order-r subgroup
    if S == (0, 0): return 0
    m = isqrt(r) + 1; table = {}; cur = (0, 0)
    for j in range(m): table.setdefault(cur, j); cur = add(cur, P)
    mP = mul(P, m); neg = (mP[0], (-mP[1]) % p) if mP != (0, 0) else (0, 0)
    g = S
    for i in range(m + 1):
        if g in table: return (i*m + table[g]) % r
        g = add(g, neg)
    return None                                                # off-curve garbage -> bad prime

def rand_point_on(bb):
    while True:
        x = int.from_bytes(os.urandom(32), 'big') % p
        y = sqrt_mod((x*x*x + a*x + bb) % p, p)
        if y: return (x, int(y))

# --- hunt weak curves: PARI point-count, trial-divide, build order-r points ---
def sieve(n):
    s = bytearray([1])*(n+1); s[0]=s[1]=0
    for i in range(2, isqrt(n)+1):
        if s[i]: s[i*i::i] = bytearray(len(s[i*i::i]))
    return [i for i in range(3, n+1) if s[i]]
SMALL = sieve(200000); mods = {}
while reduce(lambda u,v:u*v, mods, 1).bit_length() < 800:
    bb = int.from_bytes(os.urandom(32), 'big') % p
    if (4*a**3 + 27*bb*bb) % p == 0: continue
    N = int(pari.ellcard(pari.ellinit([a, bb], p)))
    for r in SMALL:
        if r in mods or N % r: continue
        P = mul(rand_point_on(bb), N // r)
        if P != (0, 0) and mul(P, r) == (0, 0): mods[r] = P

# --- query the oracle, classify good/bad, CRT ---
HOST, PORT = "TARGET_HOST", 1337
results = {}
s = socket.create_connection((HOST, PORT)); f = s.makefile('rwb', buffering=0)
def query(P):
    while b"Awaiting" not in f.readline(): pass
    f.write(f"{P[0]} {P[1]}\n".encode())
    while True:
        line = f.readline()
        if b"Shared secret" in line:
            sx, sy = [int(t) for t in line.decode().split(":")[1].strip().strip("()").split(",")]
            return (sx, sy)
        if b"Error" in line: return None
for r, P in mods.items():
    S = query(P)
    if S is None: continue
    dr = bsgs(P, S, r)
    if dr is not None: results[r] = dr

M = reduce(lambda u,v:u*v, results, 1)
d = sum(dr * (M // r) * pow(M // r, -1, r) for r, dr in results.items()) % M
print(long_to_bytes(d))       # HTB{...}
```

Running it against the live instance recovers the flag:

```
[+] d mod 138191 = 29900   (good bits=855)
[+] FLAG: HTB{...}
```

> Do **not** probe the instance with a throwaway `nc` connection first. The
> server is a forking server, and a client that disconnects leaves a child
> busy-looping "Error occured!" forever — it pegs the container's CPU until the
> instance dies. Connect once, cleanly, with the real solver.

## Why it worked

The service exposes a raw `secret · P` oracle with **no point-on-curve
validation**, and its group law ignores `b`. Every point you send is silently a
valid element of *some* invalid curve, and by choosing curves with smooth order
you reduce the secret scalar modulo small primes you fully control — then CRT
reassembles it. The `y1 == -y2` sign bug doesn't stop the attack; it only splits
primes into usable and garbage, which you route around by collecting extras.

## Fix / defense

- **Validate every incoming point is on the intended curve** before any scalar
  multiplication: check `y² ≡ x³ + ax + b (mod p)` with the *real* `b`, and
  reject the point at infinity and low-order points.
- Use a checked, constant-time library (e.g. X25519 / `cryptography`) that
  rejects invalid and low-order points instead of hand-rolling the group law.
- Never hand-write field comparisons as integer sign checks (`y1 == -y2`) — do
  the arithmetic in the field: `(y1 + y2) % p == 0`.
- Don't expose a raw `private_key · P` oracle at all; use ephemeral keys for ECDH.
