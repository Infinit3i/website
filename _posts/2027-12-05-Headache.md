## Overview

**Headache** is a Medium-difficulty [Reversing](https://www.hackthebox.com/) challenge: a single stripped 64-bit PIE ELF, no network target. Running it asks for a key and answers `Login Failed!`. The whole challenge is a stack of anti-analysis tricks layered on top of a key check that is — once you reach it — a deterministic, input-independent transform of a hardcoded array. The winning move is not to reverse the transform by hand but to instrument the program's *own* verifier and read the expected answer straight out of the comparison. The recovered key is also the flag.

This is a textbook case of [security through obscurity](https://cwe.mitre.org/data/definitions/656.html) ([CWE-656](https://cwe.mitre.org/data/definitions/656.html)): none of the layers add real cryptographic strength, and the secret the binary checks against *is* the flag it is protecting.

## The technique

Five "headaches" sit between you and the check, each defeated in one move:

1. **Corrupted ELF section headers.** `objdump -d` disassembles the `\x7fELF` magic as `.text` at virtual address 0 — pure garbage. Section headers are bogus, so you must work from the **program headers** (`readelf -lW`): the real code is the `R E` LOAD segment at vaddr `0x1000`. Carve it as a raw blob and disassemble flat, or dump it from a running process.

2. **The logic isn't in `main`.** `readelf -d` shows an `INIT_ARRAY` — a constructor function that the C runtime calls **before** `main`. That constructor (not `main`) prints the prompt, reads the key, and runs the check.

3. **Direct-syscall `ptrace` anti-debug.** The constructor calls `ptrace(PTRACE_TRACEME)` not through the PLT but as a **raw syscall**: `mov rax,1; mov rdx,0x64; xor rax,rdx` (`1 ^ 0x64 = 101` = the `ptrace` syscall number), `xor rdi,rdi` (`PTRACE_TRACEME`), `syscall`. Because it is a raw syscall, an `LD_PRELOAD` `ptrace` stub and PLT hooks **do not** intercept it. If a debugger is attached, `TRACEME` returns `-1` and the program branches to a decoy.

4. **An encrypted `main`.** On disk, `main` disassembles to junk — it is **encrypted**, and the constructor decrypts it **in place** (self-modifying code) only on the *non-debugged* path, then calls it. So you cannot even see the real check until you defeat the anti-debug. A subtlety: software breakpoints (`int3`) set *before* the decrypt get overwritten by it — use **hardware breakpoints** (`hbreak`).

5. **A second anti-debug inside `main`.** `main` computes `(edi + 2) * 100 == 100`, true only when `edi == -1` (the `ptrace` result passed in as the first argument when a debugger is present), and on that path writes a constant to address `NULL` to crash. Forcing the argument register to `0` skips it.

Past all that, the check is: for each index `i`, `expected[i] = transform(target[i], i)` — about 200 chained invertible bit operations (`rotl`/`rotr`, `not`, `neg`, `add`/`sub`/`xor`) over a fixed 21-byte array — compared against `key[i]`. It depends only on the index and a hardcoded array, never on external input, so the expected key is constant. The strings table is also seeded with **decoy flags** (`HTB{not_so_easy_lol}` in plaintext, `HTB{w0w_th4ts_c000l}` behind the inverted debug branch, and two decoy MD5 hashes) to bait `strings`.

## Solution

Rather than transcribe ~200 bit operations and risk an inversion bug, let the binary do the work. Defeat the anti-debug, then break at the per-character comparison `cmp edx, eax` (where `edx` holds the expected byte and `eax` holds your input byte), read `edx`, and force the compare to pass — collecting every expected byte.

The full solver compiles a `ptrace`-returns-0 stub, patches the constructor's anti-debug branch (`jne` `75 35` → `90 90`), runs under GDB with a hardware breakpoint at the constructor's `call main`, forces `$edi = 0`, then harvests `$edx` at the compare:

```python
#!/usr/bin/env python3
import subprocess, os, tempfile

BIN = os.path.join(os.path.dirname(__file__), "files", "headache")
d = tempfile.mkdtemp()

pt = os.path.join(d, "pt.so")
open(os.path.join(d, "pt.c"), "w").write(
    '#define _GNU_SOURCE\n#include <stdarg.h>\nlong ptrace(int r, ...){return 0;}\n')
subprocess.run(["gcc", "-shared", "-fPIC", "-o", pt, os.path.join(d, "pt.c")], check=True)

patched = os.path.join(d, "headache.patched")
b = bytearray(open(BIN, "rb").read())
assert b[0x131b:0x131d] == b"\x75\x35", "unexpected bytes at anti-debug jne"
b[0x131b:0x131d] = b"\x90\x90"
open(patched, "wb").write(b); os.chmod(patched, 0o755)

gdbpy = f'''
set pagination off
set confirm off
set environment LD_PRELOAD={pt}
starti
python
import gdb
base=int([l for l in gdb.execute("info proc mappings",to_string=True).splitlines() if "headache" in l][0].split()[0],16)
gdb.execute("hbreak *0x%x"%(base+0x134b))
gdb.execute("continue")
gdb.execute("set $edi=0")
gdb.execute("break *0x%x"%(base+0x2646))
key=[]
for _ in range(40):
    try:
        gdb.execute("continue"); pc=int(gdb.parse_and_eval("$pc"))
    except gdb.error: break
    if pc!=base+0x2646: break
    edx=int(gdb.parse_and_eval("$edx"))&0xff
    key.append(edx)
    gdb.execute("set $eax=0x%x"%edx)
print("FLAG="+bytes(b for b in key if b).decode())
end
'''
gp = os.path.join(d, "s.gdb"); open(gp, "w").write(gdbpy)
out = subprocess.run(["gdb", "-q", "-nx", "-batch", "-x", gp, patched],
                     input=b"A"*20, capture_output=True).stdout.decode(errors="replace")
flag = next((l[5:] for l in out.splitlines() if l.startswith("FLAG=")), None)
print(flag)

r = subprocess.run([BIN], input=(flag+"\n").encode(), capture_output=True).stdout.decode()
assert "Login success!" in r, "verification failed: " + r
print("[verified] original binary -> Login success!")
```

Running it harvests the 20-byte key and then **live-verifies** it against the *original*, unpatched binary (real anti-debug active):

```bash
python3 solve.py
# HTB{...}
# [verified] original binary -> Login success!
```

```bash
printf '%s\n' 'HTB{...}' | ./headache
# Initialising.....
# Enter the key: Login success!
```

Flag redacted. The key the transform produces *is* the flag.

## Why it worked

The key check is a fixed function of a hardcoded array and the byte index — it never consults anything the attacker doesn't already have. So the "secret" can be reconstructed simply by running the program's own verifier and reading the value it compares against, regardless of how much obfuscation wraps it. Every layer here — corrupted section headers, constructor-hosted logic, raw-syscall `ptrace`, self-modifying encrypted `main`, the [NULL write](https://cwe.mitre.org/data/definitions/476.html) trap, the troll flags — raises the cost of *finding* the comparison, but none of them stops you from instrumenting it once found.

## Fix / defense

Client-side checks that *contain* the answer are recoverable no matter how deeply they are obfuscated — here the binary literally ships the flag it is validating. Real protection has to move the secret out of the client: validate against a server-held value or a signature the client cannot recompute, or derive the decryption key from something a patch or debugger perturbs (a CRC of `.text`, or the `ptrace` result itself) so that tampering decrypts to garbage instead of the real code. Obscurity buys time, not security.
