## Overview

The Vault is a Medium **Reversing** challenge. You get a single stripped C++ ELF that reads a `flag.txt` and prints either *"Credentials Accepted! Vault Unlocking..."* or an *"Anti Intruder Sequence"* message. The intended solve is to recognise that the per-character check is dispatched through C++ virtual functions and simply **read the expected bytes off the comparison at runtime** — no need to reverse the 256 template classes it ships with.

## The technique

Running `strings` on the binary reveals 256 RTTI names of the form `TheCharacter<(unsigned char)N>` — one template instantiation per byte value. That's a decoy scale: the flag isn't the list, it's how `main` wires those objects together. Disassembling `main` shows a 25-iteration loop:

```
for i in 0..24:
    idx      = order_array[i]      # 25 index bytes in .rodata @ 0xe090 (NON-printable)
    obj      = objptrs[idx]        # array of 256 TheCharacter<N> object pointers @ 0x17880
    expected = obj->vfunc()        # virtual call: mov rcx,[rdi]; mov rcx,[rcx]; call rcx
    if (input[i] != expected) accepted = false     # cmp eax, ecx @ 0xc3a1
```

A purely static read of the `order_array` bytes gives garbage, because `expected` is whatever each object's virtual method *returns*, not the index. Since the check dispatches through a vtable and there are 256 of them, the clean move is to let the binary compute the expected characters itself and read them at the compare — a [reliance on client-side obfuscation](https://cwe.mitre.org/data/definitions/656.html) that a single breakpoint defeats.

## Solution

Feed a 25-character dummy `flag.txt`, break on the compare at `0xc3a1`, and dump the expected char (`$ecx`, the vtable's return value) for all 25 iterations.

Create `dump.py` (a gdb Python script):

```python
import gdb
gdb.execute("set pagination off")
gdb.execute("set disable-randomization on")
gdb.execute("starti")
maps = gdb.execute("info proc mappings", to_string=True)
base = min(int(l.split()[0], 16) for l in maps.splitlines() if l.rstrip().endswith("vault"))
gdb.Breakpoint("*%#x" % (base + 0xc3a1))
out = []
for _ in range(25):
    gdb.execute("continue")
    out.append(int(gdb.parse_and_eval("$ecx")) & 0xff)
print("FLAG=" + "".join(chr(c) for c in out))
gdb.execute("quit")
```

```bash
printf 'AAAAAAAAAAAAAAAAAAAAAAAAA' > flag.txt
gdb -q -nx -batch -x dump.py ./vault
```

The 25 harvested bytes spell the flag (`HTB{...}` — redacted). Writing it back into `flag.txt` and running `./vault` prints *"Credentials Accepted! Vault Unlocking..."*, confirming it live.

## Why it worked

Per-character validation routed through C++ virtual functions is trivially observable: you don't reverse 256 vtables, you set one breakpoint at the comparison and `continue` in a loop, reading every expected byte in order. The template-per-byte plus vtable indirection is obfuscation that adds nothing against a dynamic read.

## Fix / defense

Don't gate a secret on client-side per-character comparisons — the expected value is always recoverable at the compare instruction, whatever indirection precedes it. Authenticate against a salted hash server-side, and never ship the validation data with the program.
