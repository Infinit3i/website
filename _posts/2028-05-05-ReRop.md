## Overview

ReRop is a Hard HackTheBox **Reversing** challenge. You get a single static x86-64 binary that prompts for a flag and answers "Correct Flag!" or "Nope". The twist is that the validation logic isn't written as normal code — it's a ROP chain living in the `.data` section, executed by a stack pivot. Reverse it by resolving each gadget to a micro-op and symbolically emulating the chain with z3.

## The technique

`main` reads your input into a global buffer, strips the newline, then calls `check(&data)` where `data` points at a `.data` blob, and afterwards `puts(buf)` prints the verdict the chain wrote there. Disassembling `check` is the whole game:

```asm
check:
  lea rsp, [rdi]   ; rdi = &data (0x4c5100)
  ret              ; pivot RSP into .data and "return" into it
```

That `lea rsp,[rdi]; ret` is a [stack pivot](https://cwe.mitre.org/data/definitions/1247.html): `ret` pops the first qword of `.data` into RIP and begins executing `.data` as a **ROP chain**. So the entire flag validator is a 609-qword ROP program disguised as a data table.

> Rule of thumb: any `lea rsp,[reg]; ret` (or `mov rsp,reg; ret`) pointing into a data/bss section means that section is *code*. Disassemble it as a gadget chain, don't read it as data.

Splitting `.data` into 8-byte qwords and disassembling each unique code address builds a gadget → micro-op table:

| Gadget | Meaning |
|---|---|
| `pop rax / rdi / rsi / rdx` | load the next qword (an immediate) |
| `mov rdi,rax` / `mov rax,rdi` | register moves |
| `add/sub/xor/or/and rdi,rax` | arithmetic |
| `movzx rax,[rax]` | load a flag byte from the input buffer |
| `rdx = (rdi != 0) ? 1 : 0` | the per-character assertion |
| `add rsp,rsi if rdi<0 / if rdx!=0` | branch to the "Nope" path |
| `syscall` / `mov [rdx],rax` | I/O and stores |

Each character block computes something invertible like `((buf[i] + a) ^ b) - c` and asserts the result is `0`. On a mismatch the assertion flips `rdx` and an `add rsp` gadget skips the chain ahead to the failure path.

The key observation: because a failing check *branches away*, the correct flag is the one input for which **no branch is ever taken** — so on the success path the chain executes **linearly**, which makes symbolic emulation trivial.

## Solution

`solve.py` reads the chain with pwntools `ELF.read`, then runs a z3 symbolic emulator over the qword stream. Registers hold z3 `BitVec(64)` expressions; the flag bytes are `BitVec(8)` constrained to `0..0x7f`. `pop` sets a concrete immediate, arithmetic gadgets update `rdi`, `movzx` loads the symbolic buffer byte, and at every assertion gadget we add `rdi == 0`. The branch gadgets are ignored (success path).

```python
from pwn import ELF
from z3 import BitVec, BitVecVal, Solver, sat, simplify, is_bv_value

e = ELF('./rerop', checksec=False)
BUF = 0x4c7820
qs = [int.from_bytes(e.read(0x4c5100, 10000)[i:i+8], 'little') for i in range(0, 10000, 8)]

G = {0x450ec7:('pop','rax'), 0x401eef:('pop','rdi'), 0x409f1e:('pop','rsi'), 0x458142:('pop','rdx'),
     0x451fe0:('mov',('rdi','rax')), 0x451fe8:('mov',('rax','rdi')),
     0x451fec:('op','-'), 0x451ff0:('op','+'), 0x451ff8:('op','^'), 0x451ff4:('op','|'), 0x451ffc:('op','&'),
     0x45202f:('load',None), 0x452011:('cmp',None), 0x452000:('br',None), 0x45201e:('br',None),
     0x41aab6:('sys',None), 0x419ad8:('store',None), 0x452034:('mov',('r8','rdx')), 0x452038:('mov',('rdx','r8'))}

buf = [BitVec(f'b{i}', 64) for i in range(64)]
s = Solver()
for b in buf: s.add(b >= 0, b <= 0x7f)
reg = {r: BitVecVal(0, 64) for r in ('rax','rdi','rsi','rdx','rbx','r8')}

def const(x):
    x = simplify(x); return x.as_long() if is_bv_value(x) else None

pc = 0
while pc < len(qs):
    a = qs[pc]
    if a not in G: pc += 1; continue
    tag, arg = G[a]
    if tag == 'pop': reg[arg] = BitVecVal(qs[pc+1] & (2**64-1), 64); pc += 2; continue
    if tag == 'mov': reg[arg[0]] = reg[arg[1]]
    elif tag == 'op':
        x, y = reg['rdi'], reg['rax']
        reg['rdi'] = {'+':x+y,'-':x-y,'^':x^y,'|':x|y,'&':x&y}[arg]
    elif tag == 'load':
        ad = const(reg['rax'])
        if ad is not None and BUF <= ad < BUF+64: reg['rax'] = buf[ad-BUF] & 0xff
    elif tag == 'br': reg['rsi'] = reg['rax']          # success path: not taken
    elif tag == 'cmp': s.add(reg['rdi'] == 0); reg['rdx'] = BitVecVal(0, 64)
    elif tag == 'sys': reg['rax'] = BitVecVal(0, 64)
    pc += 1

assert s.check() == sat
m = s.model()
flag = ''.join(chr(m[b].as_long() & 0xff) for b in buf if m[b] is not None).split('\x00')[0]
print(flag)
```

29 assertions produce a 29-character flag. Always verify against the real binary:

```sh
echo 'HTB{...}' | ./rerop      # -> Correct Flag!
```

## Why it worked

Encoding the validator as a ROP chain hides it from a normal decompiler — the logic reads as an inert data table, not a function. But a ROP chain is just a linear instruction stream once every gadget is resolved, and per-character invertible arithmetic guarded by branch-on-fail is exactly the shape an SMT solver eats. It's the same idea as z3-emulating a bytecode-VM crackme; here the "machine" is a set of ROP gadgets and the "program" is the `.data` chain.

## Fix / defense

Obfuscation is not protection. A ROP-as-code validator is fully recoverable by anyone who treats the pivot target as code and models the gadgets. Anything that must stay secret cannot be reconstructible from a client-side check at all — validate secrets server-side, and don't ship the answer (even a scrambled one) in the binary.
