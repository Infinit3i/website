## Overview

`LostKey` is a medium HackTheBox **Crypto** challenge. You get `encrypt.py` and its `output.txt`. The script
multiplies a base point `G` by a secret scalar `n` on a custom elliptic curve, prints the x-coordinate of
`n·G`, and uses that same `n` to derive an AES key that encrypts the flag. The whole thing collapses to one
problem — recover `n` from `n·G` (an elliptic-curve discrete log) — and the key detail that makes it solvable
is that the author caps the scalar at 85 bits while the field prime is 256 bits.

## The technique

The AES key is derived straight from the secret scalar:

```python
key = sha1(str(n).encode('ascii')).digest()[0:16]   # AES-128 key from n
ct  = AES.new(key, AES.MODE_CBC, iv).encrypt(pad(flag, 16))
```

Recover `n`, rebuild the key, decrypt. And the assertion at the top of the script is the vulnerability:

```python
assert(n < 38685626227668133590597631)   # exactly 2**85 - 1
```

An 85-bit private key on a hand-rolled curve is far too small.

Before reaching for anything clever, rule out the standard "degenerate curve" shortcuts — each has a cheap
test, and knowing they *don't* apply tells you what does:

| Check | Test | Result |
|---|---|---|
| Singular curve (node/cusp) | Weierstrass discriminant Δ = 0? | Δ ≠ 0 → no |
| Anomalous ([Smart's attack](https://cwe.mitre.org/data/definitions/327.html)) | is #E = p, i.e. `p·G == O`? | `p·G ≠ O` → no |
| Supersingular (MOV pairing) | is #E = p+1, i.e. `(p+1)·G == O`? | `(p+1)·G ≠ O` → no |

All three fail — this is a genuine elliptic curve. So it's a real ECDLP, but with a tiny key. That combination
is exactly what **improved Pohlig-Hellman** eats.

Factoring the group order (via PARI's `ellcard` + `factor`) shows it is only *partially* smooth:

```
#E = 3² · 59 · 14771 · 27733 · 620059697 · 2915987653003935133321 · 257255080924232005234239344602998871
        \____________ small (≤30-bit) ___________/   \___ 72-bit ___/   \______ 118-bit ______/
```

The two big primes on the right would each need a hopeless discrete-log search — but we never touch them.
Solve the discrete log only over the small factors: that pins `n` modulo `M ≈ 2⁶⁷`. Since `n < 2⁸⁵`, only
`2⁸⁵ / 2⁶⁷ = 2¹⁸ ≈ 262 000` candidates remain for the high bits, and a direct scalar-multiply check finds the
right one. This uses [CWE-327](https://cwe.mitre.org/data/definitions/327.html): a broken/risky crypto
construction — a smooth-order fragment that is harmless against a full-entropy key becomes a full break against
an undersized one.

## Solution

Map the custom `add`/`double` code to standard short-Weierstrass invariants (`a1=0`; `a3` from the doubling
denominator; `a2` from the `R.x` constant; `a4` from the numerator), recover `a6` by plugging `G` into the
curve equation, then run the attack. Kali has no SageMath, so `cypari2` (bundled PARI) does the heavy lifting:

```python
import cypari2
from hashlib import sha1
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad

pari = cypari2.Pari()
pari.allocatemem(1 << 30)          # ellcard overflows PARI's default 8 MB stack — grow it FIRST

p  = 101177610013690114367644862496650410682060315507552683976670417670408764432851
a2 = 208913474430283759938044884583915265967
a3 = 3045783791
a4 = 177776968102066079765540960971192211603
a6 = 308081941914167831441899320643373035841     # recovered by plugging G into the curve equation
E  = pari.ellinit([0, a2, a3, a4, a6], p)

Gx = 14374457579818477622328740718059855487576640954098578940171165283141210916477
Gy = 97329024367170116249091206808639646539802948165666798870051500045258465236698
G  = pari([Gx, Gy])

Gnx = 32293793010624418281951109498609822259728115103695057808533313831446479788050
Gn  = pari([Gnx, pari.ellordinate(E, Gnx)[0]])    # lift a valid y for Gn (either root works)

order = int(pari.ellcard(E))

# Pohlig-Hellman over ONLY the small (<=30-bit) prime-power factors
easy = [3**2, 59, 14771, 27733, 620059697]
res, mods = [], []
for q in easy:
    cof = order // q
    Gq  = pari.ellmul(E, G,  cof)                 # point of order dividing q
    Pq  = pari.ellmul(E, Gn, cof)                 # equals n * Gq
    oq  = int(pari.ellorder(E, Gq))
    res.append(int(pari.elllog(E, Pq, Gq, oq)))   # n mod oq
    mods.append(oq)

# CRT the residues -> n mod M  (M ~ 2^67)
M = 1; r = 0
for d, m in zip(res, mods):
    g = pow(M % m, -1, m)
    r += M * (((d - r) * g) % m)
    M *= m
r %= M

# brute the residual high bits: n = r + k*M, with n < 2^85
BOUND = 38685626227668133590597631                # 2^85 - 1
cand = r
while cand <= BOUND:
    if int(pari.ellmul(E, G, cand)[0]) == Gnx:     # match on x-coordinate alone
        n = cand
        break
    cand += M

# rebuild the AES key from n and decrypt
key = sha1(str(n).encode('ascii')).digest()[:16]
ct  = bytes.fromhex(open('output.txt').read().split('Ciphertext: ')[1].split()[0])
iv  = bytes.fromhex("baf9137b5bb8fa896ca84ce1a98b34e5")
print(unpad(AES.new(key, AES.MODE_CBC, iv).decrypt(ct), 16).decode())
```

This recovers an 80-bit scalar in about five seconds and prints the flag `HTB{...}`.

## Why it worked

The break needed two mistakes to line up, and neither alone is fatal. The curve order was only **partially
smooth** — normally you'd shrug, because the leftover 72- and 118-bit primes make the full discrete log
infeasible. But the private scalar was **undersized** (`n < 2⁸⁵`), which turns the smooth part from "not
enough" into "more than enough": once `n` is known modulo a 67-bit number, only about `2¹⁸` candidates for the
top bits survive, and a direct scalar-multiply check finishes them off. Comparing x-coordinates means the
y-coordinate of `n·G` is never even required.

## Fix / defense

- Use a vetted, **prime-order** (or tiny-cofactor) standard curve — `secp256r1`, Curve25519 — never a
  hand-built Weierstrass curve whose order you didn't audit.
- Draw private scalars **full-size and uniform** in `[1, ord(G))`. Never clip the key well below the field size.
- At key generation, factor `#E` and reject any curve whose smooth part exceeds a safety margin — that single
  check would have caught this.
