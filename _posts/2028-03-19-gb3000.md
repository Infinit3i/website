## Overview

gb3000 ships a single Game Boy ROM. Boot it and you get an empty framed canvas — it's a tiny
GB paint/plotter. You move a cursor with the d-pad and confirm; a *correct* drawing unlocks a
"win" screen that draws the flag. You never actually have to make the right drawing, though —
the win screen is decoded with a one-byte key you can brute-force straight out of the ROM.

![The empty canvas](/assets/Images/gb3000-canvas.png)

## The technique

`radare2 -a gb gb3000.gb` disassembles the Sharp LR35902 cleanly, and PyBoy
(`pip install pyboy pillow`) runs it headless for memory/VRAM inspection. The entry at `0x100`
jumps to `0x150`, which memcpys a font + tilemap into VRAM to draw the empty box.

The main loop at `0x17c` reads the joypad and branches: if the confirm button isn't pressed it
runs the drawing handler; if it is, it runs four gate checks against WRAM, and if they pass it
draws the win screen — but through a decoder routine (`0x029e`) rather than a plain copy:

```
KEY = (sum of WRAM 0xc001 .. 0xc010) & 0xff
for each source byte:  out = (src + KEY) & 0xff
```

That's an **additive cipher keyed by a single byte** — the sum of the drawing state. However
much state feeds it, the key is one byte, so the correct drawing is irrelevant: there are only
256 possible keys.

## Solution

The correct key must decode the win tilemap into valid tile indices. The win screen loads 67
tiles (`0x430 / 16`), so every decoded tilemap byte should land in `[0, 66]` — a free oracle
for the right key. Score all 256 and one wins outright, then render the decoded tilemap+font:

```python
from PIL import Image
d = open("gb3000.gb", "rb").read()
NT = 0x430 // 16                                   # 67 loaded tiles
K = max(range(256),
        key=lambda k: sum((b + k) & 0xff < NT for b in d[0x0b65:0x0b65 + 0x240]))
# K == 148  (a perfect 576/576 fit)

tiles = bytes((b + K) & 0xff for b in d[0x03f5:0x03f5 + 0x430])
tmap  = bytes((b + K) & 0xff for b in d[0x0b65:0x0b65 + 0x240])
img = Image.new("L", (32 * 8, 18 * 8)); px = img.load(); pal = [255, 170, 85, 0]
for ty in range(18):
    for tx in range(32):
        t = tiles[tmap[ty * 32 + tx] * 16:][:16]
        for r in range(8):
            b0, b1 = t[2 * r], t[2 * r + 1]
            for c in range(8):
                px[tx*8 + c, ty*8 + r] = pal[((b1 >> (7-c)) & 1) << 1 | ((b0 >> (7-c)) & 1)]
img.save("win.png")     # a flag icon + "CORRECT!!!" + the flag
```

`win.png` renders a flag icon, "CORRECT!!!", and the flag `HTB{...}` in a 16-pixel font — the
content is a nice in-joke about the d-pad draw sequence and the challenge name.

## Why it worked

The author "encrypted" the win screen with a key derived from the exact correct drawing — but
the key is a *sum*, applied as one constant byte to every source byte. A one-byte keyspace is
256 candidates, and the tile-index validity of the decoded map hands you the right one for free.
You skip the entire drawing puzzle and read the flag directly from the ROM.

## Fix / defense

- A sum-of-state key is one byte no matter how much state feeds it — never let a large secret
  collapse to a tiny effective keyspace; derive keys with a real KDF over the full state.
- Don't expose a decode-validity oracle: "all tile indices are in range" instantly reveals the
  key. Authenticate the payload instead of letting structure leak correctness.
