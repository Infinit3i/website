## Overview

Joker is a HackTheBox Mobile challenge (Hard). You get a single `joker.apk` and no server — pure reverse engineering. The app is a **multi-stage dropper**: the flag sits under three layers of "encryption," each decrypted by the previous stage. The saving grace is that **every key ships inside the app**, so the whole chain unpacks statically — we never run it, which also sidesteps its anti-debug and timestamp traps. This is [CWE-656](https://cwe.mitre.org/data/definitions/656.html): reliance on security through obscurity.

## The technique

Four layers, peeled in order:

- **Layer 0 — decoy.** `MainActivity` is a tic-tac-toe game. The real logic runs from a `ContentProvider` (`JokerBr`) whose `onCreate()` is gated on `System.currentTimeMillis()/1000 == 1732145681` — a timestamp trigger that only matters if you *run* the app. Every string in the app is scrambled by one repeating-key XOR helper.
- **Layer 1 — AES to a native library.** An assets file is decrypted with `AES/CBC/PKCS5Padding` where **key and IV are both** `SHA1(keyString)[:16]` (`SHA1` computed twice on the same input, so key == IV). The result is an ARM64 `.so`, which the app `System.load()`s and calls into via a JNI native `goto2()`.
- **Layer 2 — native XOR to a second DEX.** The native library has `ptrace`/`fork` anti-debug and single-byte-XOR strings (with the keys stored right next to the data in the GOT). Its decrypt routine XORs a second assets file with a repeating key that is literally the banner string it would have printed — `"The flag is:"` — producing a second-stage `classes.dex`.
- **Layer 3 — the flag.** That DEX contains a trivial class that prints `HTB{ + host + }`.

## Solution

The full chain reproduced offline — AES → XOR → DEX — no device or emulator:

```python
import hashlib
from Crypto.Cipher import AES

ASSETS = "files/apk_x/assets/io/m/l/l/d"

# stage 1: AES-decrypt the 301 asset to the native .so (key == iv == SHA1(keystring)[:16])
key_str = "ma1"+"7FEC"+"2_l"+"Yuo"+"NQ"+"$_To"+"T99u_e0kINhw_Bzy"
h = hashlib.sha1(key_str.encode()).digest()[:16]
so = AES.new(h, AES.MODE_CBC, h).decrypt(open(f"{ASSETS}/eibephonenumberse301.txt","rb").read())
so = so[:-so[-1]]
assert so[:4] == b"\x7fELF"

# stage 2: XOR-decode the 300 asset (goto2's repeating key) to a dex
KDF = b"The flag is:"
raw = open(f"{ASSETS}/eibephonenumberse300.txt","rb").read()
dex = bytes(raw[i] ^ KDF[i % len(KDF)] for i in range(len(raw)))
assert dex[:4] == b"dex\n"

# stage 3: the dex's Payload2 prints HTB{ + host + }
host = "C0mm4nd_and_C0ntr0l_Server"
print(f"HTB{{{host}}}")
```

Getting there needs `jadx` (decompile both DEX layers) and `radare2` for the ARM64 `.so`. A gotcha: Kali's stock `objdump` has no aarch64 target and produces empty disassembly — use `r2 -e asm.bits=64 -e bin.relocs.apply=true`, where applying relocations is what resolves the GOT pointer pairs (each obfuscated string sits next to its 1-byte XOR key) that reveal the second asset path and the native key material.

Running the chain yields `HTB{...}`.

## Why it worked

None of the three encryption layers protects a real secret. The AES key is `SHA1` of a string embedded in the app; the XOR key is the banner string the app was going to print anyway; the native library's own strings are single-byte-XOR with the keys sitting beside them in the GOT. Obfuscation, packing, and anti-debug raise the effort but ship everything the analyst needs — the definition of [CWE-656](https://cwe.mitre.org/data/definitions/656.html).

## Fix / defense

- A secret a mobile app must protect on the client is always extractable — keep it server-side and validate there.
- If you encrypt on-device, never derive the key and IV from the same value, use a real KDF (not raw `SHA1` of a hardcoded string), and use a fresh random IV per message.
- Treat obfuscation and anti-debug as cost-raising, not as a control; a layered dropper is fully reversible by decompiling each stage and replaying its transform.
