## Overview

The PROM is a Medium HackTheBox Hardware challenge. A TCP service emulates an **AT28C16** parallel EEPROM at the pin level and asks you to "uncover the EEPROM's secrets." Reading the normal 2KB memory array returns all zeros — the flag is stashed in the chip's hidden **Device Identification block**, which the [device only exposes](https://cwe.mitre.org/data/definitions/1191.html) when you drive an address line to a non-standard 12V.

## The technique

The service prints the AT28C16 DIP pinout and offers pin-level commands:

```
set_address_pins(address)   # A10..A0 voltages, MSB-first
set_ce_pin(volts) / set_oe_pin(volts) / set_we_pin(volts)
read_byte()                 # -> "Read 0xNN at address 0xAAA"
```

The control pins `!CE`, `!OE`, `!WE` are active-low; logic 1 = 5V, logic 0 = 0V. A normal read is `!WE=5` (write disabled), `!OE=0` (output enabled), `!CE=0` (chip enabled), set the address, `read_byte()`. But sweeping the whole address space that way returns `0x00` for every byte — the array is blank.

The AT-series EEPROMs expose a manufacturer **Device Identification / silicon-ID block** that answers only when address line **A9 is pulled to ~12V** — the high voltage used for chip-ID reads and programming mode. Set A9 to 12V and read the top 32 bytes, **0x7E0–0x7FF**: those hold the flag as ASCII.

## Solution

```python
def addr_list(a):
    bits = [(a >> (10 - i)) & 1 for i in range(11)]     # MSB-first: index0=A10 .. index10=A0
    v = ['5' if b else '0' for b in bits]
    v[1] = '12'                                          # A9 -> 12V (Device ID block)
    return '[' + ','.join(v) + ']'

# setup: set_we_pin(5), set_oe_pin(0), set_ce_pin(0)
for a in range(0x7E0, 0x800):
    send('set_address_pins(%s)' % addr_list(a))
    send('read_byte()')
# parse "Read 0xNN at address 0xAAA", decode the 32 bytes as ASCII -> HTB{...}
```

One practical catch: each command has multi-second latency and the emulator instance is short-lived, so reading byte-by-byte with a wait per command can't finish. **Pipeline** the commands — send every `set_address_pins`+`read_byte` without waiting for the prompt, then read the whole stream at once (a full 2048-byte dump returns in about nine seconds). Only 32 bytes are needed here, decoding straight to the flag (`HTB{...}`, redacted).

## Why it worked

The secret's only protection is obscurity: it lives in a chip block that answers exclusively when a documented non-standard voltage is applied to an address pin. There's no authentication and no crypto — the data is one 12V rail away from disclosure.

## Fix / defense

- Never store secrets in a chip's manufacturer-ID/test block; anyone who applies the documented access voltage can read it.
- Blow the device's lock fuse after provisioning and disable high-voltage ID/programming access in the field.
- Treat any special-voltage or strap-entered test/programming mode as an untrusted, unauthenticated read path.
