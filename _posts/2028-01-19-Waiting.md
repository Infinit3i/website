## Overview

Waiting is a Medium **Mobile** challenge. You get a single Android APK whose description brags that it stores a secret "securely even in case the application has been tampered." That sentence is the whole hint: the app is packed with anti-tamper checks, and the intended solve is to **ignore the runtime entirely** and lift the secret straight out of the native library statically. We recover it by emulating a *tiny slice* of the native code with Unicorn — no device, no emulator, no Frida.

## The technique

An APK is just a ZIP. Unzipping it yields `classes.dex` plus native libraries, notably `lib/*/libsecrets.so`. Decompiling the DEX (with **androguard**) shows the app flow:

- `MainActivity` → `MenuActivity` → `SecretActivity`.
- `SecretActivity.onCreate()` sets a `TextView` to `new Secrets().getdxXEPMNe()`.
- `Secrets` is `System.loadLibrary("secrets")` plus `public final native String getdxXEPMNe();`.

Everything *else* in the Java is a decoy anti-analysis layer, an instance of [insufficiently protected client-side secrets](https://cwe.mitre.org/data/definitions/321.html) dressed up to look hard to reach:

- A root / developer-options check that reads `Settings.Secure.ADB_ENABLED` and shells out to `getprop` / `which su`. Its strings are hidden with a tiny XOR obfuscator: `char ^ 47191 ^ (i % 65535)`.
- A `BroadcastReceiver` that calls `Process.killProcess()` if USB debugging is enabled.
- A `getReferrer().endsWith(packageName)` check so you can't just launch the secret screen with an `am` intent.

Solve this *dynamically* and you fight all of that. The winning move: the secret is compiled into `libsecrets.so`; extract it without running the app.

## Solution

Find the JNI export — JNI naming is `Java_<pkg>_<class>_<method>`:

```bash
objdump -T lib/x86_64/libsecrets.so | grep -i getdx
# Java_com_example_waiting_Secrets_getdxXEPMNe
```

Disassembling the function (`objdump -d`) reveals two parts. A long, **call-free preamble** (~700 bytes of `lea`/`movq`/`punpcklqdq`/`movdqa`) materializes **two arrays of 48 `char*` pointers** on the stack — each pointing at a single scattered byte in `.rodata` (that scattering is why `strings` finds nothing). Then a decode loop:

```
mov 0x1f0(%rsp,%rbx,8),%rax   ; tableA[i]
mov 0x70(%rsp,%rbx,8),%rcx    ; tableB[i]
movzbl (%rcx),%r13d           ; *tableB[i]
xor    (%rax),%r13b           ; ^= *tableA[i]
cmp    $0x30,%rbx             ; 48 iterations
```

So the algorithm is simply `secret[i] = *tableA[i] ^ *tableB[i]` for `i` in 0..47, with `tableA` at `rsp+0x1f0` and `tableB` at `rsp+0x70`.

The tail of the function builds a C++ `std::string` and calls `env->NewStringUTF` — painful to emulate (fake JNIEnv, allocator, and so on). We don't need any of it. The preamble that fills the two pointer tables is pure register/stack arithmetic with **zero calls**, so we emulate from the function entry and **stop right before the loop**, then read the tables and do the XOR in Python.

Create `solve.py`:

```python
import struct, lief
from unicorn import *
from unicorn.x86_const import *

SO, FUNC, STOP = "libsecrets.so", 0xeb90, 0xf179   # STOP = first insn of the loop setup
b = lief.parse(SO)
uc = Uc(UC_ARCH_X86, UC_MODE_64)
pg = lambda x: x & ~0xfff; up = lambda x: (x + 0xfff) & ~0xfff

# map LOAD segments at their virtual addresses (so rip-relative lea resolve correctly)
for s in b.segments:
    if s.type == lief.ELF.Segment.TYPE.LOAD:
        va = pg(s.virtual_address); sz = up(s.virtual_address + s.virtual_size - va)
        uc.mem_map(va, sz); uc.mem_write(s.virtual_address, bytes(s.content))

ST = 0x7fff0000; uc.mem_map(ST - 0x100000, 0x200000); uc.reg_write(UC_X86_REG_RSP, ST)
FS = 0x60000000; uc.mem_map(FS, 0x1000)      # scratch for the `mov %fs:0x28` stack-canary read
uc.reg_write(UC_X86_REG_FS_BASE, FS); uc.reg_write(UC_X86_REG_RDI, FS)

uc.emu_start(FUNC, STOP)                       # run just the table-building preamble
sp = uc.reg_read(UC_X86_REG_RSP)               # rsp after push*6 + sub 0x378

out = bytearray()
for i in range(0x30):                          # 48 bytes
    a = struct.unpack("<Q", uc.mem_read(sp + 0x1f0 + i*8, 8))[0]   # tableA[i]
    k = struct.unpack("<Q", uc.mem_read(sp + 0x70  + i*8, 8))[0]   # tableB[i]
    out.append(uc.mem_read(a, 1)[0] ^ uc.mem_read(k, 1)[0])
print(out.decode())
```

Run it:

```bash
python3 solve.py
# HTB{...}
```

## Why it worked

The obfuscation's strength — scattered bytes plus XOR so `strings`/`grep` fail — is irrelevant once you locate the *deterministic* reconstruction code. Because the byte-assembly is call-free, a partial emulation of ~700 instructions reproduces exactly what the device would compute, **without a device and without triggering a single anti-tamper check**, because none of those checks live in the reconstruction path.

The general lesson: when a native library rebuilds a secret at runtime, you rarely need to emulate the whole JNI call. Isolate the self-contained decode region, emulate just that with Unicorn, and read the result out of emulated memory. Anti-tamper and anti-debug that run *elsewhere* never execute, so they can't stop you.

## Fix / defense

- Do not treat client-side native code as a secret store — anything shipped in the APK is extractable. Keep real secrets server-side and release them only after server-side attestation (Play Integrity / SafetyNet) that you verify on the backend.
- If a token must ship in the app, bind its usefulness to server-verified device/app integrity so a statically-lifted copy is worthless off-device.
