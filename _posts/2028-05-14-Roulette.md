## Overview

Roulette is an **Insane** HackTheBox **Crypto** challenge. You connect to a casino that
spins a wheel `0..31` each round with a home-made `Twister` PRNG and bet Even / Odd /
exact-Number. Start with 50 coins, reach 10,000,000,000,000, and it hands over the flag.
The whole break is that the generator is built only from XOR and bit-rotations, which makes
it **affine over GF(2)** — recover its state from a few hundred observed spins with linear
algebra, then predict every wheel and bet the exact number all-in until you blow past the
target.

## The technique

The generator's state update and output tempering look like this:

```python
def twist(self):
    for i in range(N):
        self.STATE[i] ^= rol(self.STATE[(i+1) % N], 3)
        self.STATE[i] ^= rol(self.STATE[(i+M) % N], b - 9)
        self.STATE[i] ^= MAGIC

def rand(self):
    y = self.STATE[self.index]
    y ^= rol(y, 7)
    y ^= rol(y, b - 15)
    return y & mask
```

Every operation is XOR, a fixed rotation, or XOR with a constant — and none of those are
nonlinear. XOR is addition in GF(2); `rol(x, d)` only permutes bit positions (output bit
`k` is input bit `(k-d) mod 32`); the constant `MAGIC` only flips the affine offset. So each
of the 128×32 = 4096 initial state bits is an unknown over GF(2), and **every output bit is
a fixed linear combination of those unknowns plus a constant**. A PRNG with no nonlinearity
leaks its entire state to linear algebra — this is a [use of a cryptographically weak
PRNG](https://cwe.mitre.org/data/definitions/338.html).

The wheel exposes `rand() % 32` — the low 5 bits — every round. Collect enough of those and
you have an over-determined linear system.

## Solution

Run the generator a **second time symbolically**: instead of 32-bit integers, each state bit
is a bit-vector (a Python `int` — bits `0..4095` mark which unknowns are XORed in, bit `4096`
is the affine constant). This emits, per draw, the exact linear form of each observed bit.
Then bet Odd for 1 coin each round to farm 820 draws (a fair ±1 walk survives ~92% of the
time), giving 820×5 = 4100 equations over 4096 unknowns. Gauss-Jordan over GF(2) with each
equation stored as one big integer recovers a consistent state — you get rank 3840, not full
rank, and it *still works*, because the future spins you want to predict lie in the row-span
of the equations you already have.

```python
class SymTwister:                 # same generator, over GF(2) bit-vectors
    def __init__(self):
        self.index = N
        self.STATE = [[1 << (i*b + j) for j in range(b)] for i in range(N)]
    # twist()/rand() identical to the target, but forms are ints; observe y[:5]

def solve(vals):                  # 820 observed rand()%32 values -> initial state
    sym = SymTwister()
    forms = [sym.rand()[:5] for _ in range(len(vals))]
    pivots = {}
    for d, v in enumerate(vals):
        for j in range(5):
            f = forms[d][j]
            rhs = ((v >> j) & 1) ^ ((f >> CONST) & 1)
            cur = (f & COEFF) | (rhs << NB)
            while (coeff := cur & COEFF):
                p = (coeff & -coeff).bit_length() - 1
                if p in pivots: cur ^= pivots[p]
                else: pivots[p] = cur; break
    # back-substitute (free vars = 0), rebuild STATE, run forward to predict
```

The instances are short-lived, so the observation phase is **pipelined** — blast all
`b"2\n1\n" * 820` bets at once, bulk-read, and regex every `The wheel stops at (\d+)`. Only
the endgame is sequential: reconstruct the state, fast-forward past the 820 observed rounds,
then bet the exact predicted number all-in (`money → 11 × money` per win). From ~48 coins it
takes exactly 11 consecutive correct predictions to cross 10^13:

```
[+] round 821: pred 18 HIT, money=528
...
[+] round 831: pred 14 HIT, money=13694960189328
FLAG: HTB{...}
```

## Why it worked

The `Twister` was designed to *look* like a strong stateful PRNG — a large 4096-bit state,
a Mersenne-style twist, output tempering. But the designer only reached for XOR and
rotations, which are both linear over GF(2). Linearity composes: a rotation of a linear form
is a linear form, an XOR of linear forms is a linear form, and even truncating to the low 5
bits just selects 5 of the linear equations. Nothing ever mixes the unknowns nonlinearly, so
the mapping *initial state → any future output bit* is a matrix you can solve. Truncation
doesn't help the defender — it only means you need proportionally more draws to gather enough
rows.

## Fix / defense

Never build a secret-bearing generator from only XOR + rotations/shifts + constants. Derive
the wheel from a CSPRNG seeded server-side, and never expose raw generator outputs at scale:

```python
import secrets
def spin():
    return secrets.randbelow(32)   # CSPRNG per draw, no recoverable state
```

If a custom generator is genuinely required, it needs a real nonlinearity (an S-box, a
modular multiply, data-dependent rotations) so that outputs are no longer a linear function
of the state.
